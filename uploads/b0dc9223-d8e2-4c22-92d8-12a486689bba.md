## 一、DSL工作流引擎

### 1.1 背景

在AI数据集处理场景中，数据处理流水线由多个算子节点组成（比如：文件上传 → 文本清洗 → 敏感词过滤 → 格式转换）。每个算子的元数据（编码、名称、输入输出类型、业务参数）是固定的，但算子数量多（项目中有155+个算子），如果每个算子都手写配置类，扩展成本高、维护困难。

### 1.2 原理

#### 1.2.1 策略模式 + 枚举驱动

用 `OperatorTypeEnum` 枚举定义所有算子的元数据，每个枚举常量包含：
- `code`：算子唯一ID（哈希值），用于和外部Python调度引擎对接
- `name`：英文标识，前端传参用
- `cname`：中文名，界面展示
- `type`：算子类型（SOURCE源算子 / PROCESSOR处理算子）
- `inputType / outputType`：数据类型（TEXT、IMAGE、VIDEO、AUDIO），用于校验算子间能否连接
- `description`：算子描述

```java
// OperatorTypeEnum.java（155个算子，1624行）
```

```java
private static List<Map<String, Object>> buildDynamicEdges(List<NodeInfo> nodeInfos) {

        NodeInfo current = nodeInfos.get(i);
        NodeInfo next = nodeInfos.get(i + 1);
        edges.add(buildEdge(current.getOutputPortId(), next.getInputPortId()));
    }
    return edges;
```

### 1.3 项目应用场景

项目中实际使用场景：用户在前端可视化编排算子节点（假设3个节点 A→B→C），系统需要：

1. **校验阶段**（`WorkflowBuildService`）：验证节点列表是否合法（算子是否存在、数据类型是否兼容、数据源配置是否完整）
2. **转换阶段**：把前端请求转为内部 `NodeConfig` 对象
3. **构建阶段**：工厂类根据算子类型生成完整JSON DSL（包含节点定义、连线、算法配置）
4. **提交阶段**：调用外部Python调度引擎创建任务、执行、轮询状态

```java
// WorkflowBuildService.java（365行）

    // 1. 参数校验
    validateRequest(request);

    // 2. 节点配置转换
    List<NodeConfig> nodeConfigs = convertToNodeConfigs(request.getNodes());

    // 3. 工厂构建完整请求

            request.getProcCode(), request.getTaskId(), request.getTaskName(),
            request.getVersion(), request.getProjectCode(), nodeConfigs,
            buildTaskConfigOptions(request));

    return saveRequest;
}
```

### 1.4 为什么要这样处理

**问题**：155个算子如果每个都手写配置类，新增算子需要改工厂代码，扩展成本高，容易出错。

**解决方案**：枚举定义元数据 + 工厂自动构建。源算子和处理算子的JSON结构不同（在工厂中根据 `hasInput()` 区分），工厂类根据枚举属性自动决定生成哪种节点——**新增算子只需在枚举加一条记录，不需要改任何工厂逻辑**。

### 1.5 已解决的问题

1. **算子元数据分散**：原来元数据放数据库，每次请求都要查库；改用枚举后编译期检查，零IO开销
2. **DSL结构复杂**：JSON结构包含nodes、edges、algoConfig、ioConfig等多层嵌套；工厂类分方法构建（`buildSourceNode` / `buildProcessorNode` / `buildDynamicEdges`），代码清晰可维护
3. **前端传参不一致**：前端可能传 `operatorName` 也可能传 `operatorCode`；工厂支持两种方式查找算子

### 1.6 优化的地方

1. **DSL模板缓存**：当前每次请求都重新生成JSON字符串，可以将不变的DSL模板部分缓存起来，只替换动态参数
2. **算子分类索引**：当前 `getByCode()` / `getByName()` 是线性遍历155个枚举，性能O(n)；可以按type建立分组索引优化到O(1)
3. **可视化连线参数化**：`buildDynamicEdges` 简单按顺序连线，如果需要支持更复杂的多输入多输出场景，需要更灵活的连线DSL

## 二、多节点增量执行与崩溃恢复

### 2.1 背景

数据集处理任务可能有多个算子节点，执行时间较长（分钟到小时级别）。如果执行过程中服务崩溃，需要从断点恢复而不是从头开始，否则会导致：
- 数据重复计算，浪费资源
- 中间结果丢失
- 已完成的步骤被重复执行

### 2.2 原理

#### 2.2.1 两两增量执行

每个任务节点有 `dataSetCode`（数据集编码）字段，表示该节点的输出结果：

```java
// UseWorkFlowServiceImpl.java

        CleaningTaskNode second = executionNodes.get(segmentIndex + 1);

            if (isReady) {

                segmentIndex++;
                continue;
            }
        }

        executeTwoNodesWorkFlow(task, first, second, httpRequest, null);
        segmentIndex++;
    }
}
```

#### 2.2.2 崩溃恢复 — 三层判断

应用重启时，`TaskRecoveryService` 扫描所有RUNNING状态的任务：


**断点定位逻辑**：

```java
private void checkXhaiStatus(CleaningTask task, List<CleaningTaskNode> nodes) {
    // 遍历节点找到断点位置
    CleaningTaskNode interruptedNode = null;   // 有taskInstanceId但没有dataSetCode → 中断节点
    CleaningTaskNode lastCompletedNode = null; // 有dataSetCode → 已完成节点

    for (CleaningTaskNode node : nodes) {
        if (node.getTaskInstanceId() != null) {
            if (node.getDataSetCode() != null) {
                lastCompletedNode = node;      // 完成
            } else {
                interruptedNode = node;         // 中断
            }
        }
    }

    if (interruptedNode != null) {
        // 查询外部平台该节点的真实状态
        String statusCode = xhaiCookieService.getTaskInstanceStatus(interruptedNode.getTaskInstanceId(), cookie);
        TaskInstanceStatusEnum status = TaskInstanceStatusEnum.getByCode(statusCode);

        if (status.isSuccess()) {
            // 外部已完成但没回写结果 → 回写结果 + 从断点继续
            updateNodeFromXhai(interruptedNode, cookie);
            continueFromNode(task, nodes, interruptedNode);
        } else if (status.isFailed()) {
            markTaskFailed(task, "外部执行失败");
        } else {
            // 还在跑 → 等下次恢复检查
        }
    }
}
```

#### 2.2.3 防并发恢复 — ConcurrentHashMap

```java
private static final ConcurrentMap<String, Boolean> RECOVERING_TASKS = new ConcurrentHashMap<>();

private void recoverSingleTask(CleaningTask task) {
    // putIfAbsent 原子操作，防止多个恢复任务同时处理同一个任务
    if (RECOVERING_TASKS.putIfAbsent(taskId, Boolean.TRUE) != null) {
        log.info("该任务正在被恢复，跳过");
        return;
    }
    try {
        doRecoverSingleTask(task);
    } finally {
        RECOVERING_TASKS.remove(taskId);
    }
}
```

### 2.3 项目应用场景

用户点击"执行清洗任务"，任务可能包含5个算子节点。执行到第3个节点时服务崩溃（或者机器重启），应用重启后：

1. 定时任务扫描所有 RUNNING 状态的任务
2. 找到第1、2个节点已完成（有 `dataSetCode`），第3个节点中断（有 `taskInstanceId` 但没有结果）
3. 查询外部平台，发现第3个节点实际已完成但结果没回写
4. 回写第3个节点结果，然后从第3个节点作为输入继续执行第4、5个节点

### 2.4 为什么要这样处理

**问题**：如果崩溃恢复需要从头开始执行，假设一个任务有10个节点，执行了9个崩溃了，重新跑需要再花9倍时间，数据可能重复处理。

**解决方案**：
- 两两执行 + 每完成一对立即持久化状态到数据库，节点之间天然有断点
- 外部平台独立存储执行状态，恢复时查外部平台而不是只看本地数据库
- 增量恢复，只执行未完成的后续节点

### 2.5 已解决的问题

1. **状态不一致**：本地数据库说任务RUNNING，外部平台可能已完成；恢复时优先查外部平台真实状态
2. **重复提交**：节点 `submitting=true` 但提交过程中崩溃了，下次恢复会重复提交；设计了10分钟超时强制清理逻辑
3. **新启动任务误判**：刚启动的任务状态也是RUNNING，但实际正在正常执行；设计了3分钟保护期

### 2.6 优化的地方

1. **外部平台轮询优化**：当前用固定间隔轮询，可以改为指数退避轮询（初始间隔短，后续逐步拉长）
2. **断点精度提升**：当前最小恢复单元是节点对，可以支持更细粒度的算子内部步骤恢复
3. **恢复任务优先级**：当前所有RUNNING任务平等处理，可以按任务创建时间或紧急程度排序

## 三、多格式文档解析

### 3.1 背景

数据集来源多样，用户可能上传txt、doc、docx、pdf等不同格式的文档。每个格式的解析方式不同（txt纯文本、docx是ZIP+XML、pdf是二进制格式）。需要统一接口，屏蔽底层格式差异，让调用方无感知的获取文档文本内容。

### 3.2 原理

#### 3.2.1 工厂模式

```java
// DocumentParserFactory.java（93行）
public class DocumentParserFactory {

        return parser;
```

#### 3.2.2 多级回退链

```java
// ZipUtil.java（684行）
public String extractTextContent(String fileName, byte[] fileBytes) {
    // 第一层：正常解析
    try {
        DocumentParser parser = DocumentParserFactory.getParserByFileName(fileName);
        List<String> lines = parser.parseToLines(new ByteArrayInputStream(fileBytes));
        return String.join("\n", lines);
    } catch (Exception e) { /* 降级到下一层 */ }

    // 第二层：纯文本格式直接UTF-8读取
    if (isTextFile(fileName)) {
        return new String(fileBytes, StandardCharsets.UTF_8);
    }

    // 第三层：无扩展名，按UTF-8文本处理
    if (!fileName.contains(".")) {
        return new String(fileBytes, StandardCharsets.UTF_8);
    }

    // 第四层：交叉尝试（.doc实际是docx格式）
    return tryAlternateParsers(fileName, fileBytes);
}

private String tryAlternateParsers(String fileName, byte[] fileBytes) {
    if (fileName.endsWith(".doc")) {
        // .doc文件 → 尝试用docx解析器
        try { new DocxParser().parseToLines(new ByteArrayInputStream(fileBytes)); } catch {}
    }
    if (fileName.endsWith(".docx")) {
        // .docx文件 → 尝试用doc解析器
        try { new DocParser().parseToLines(new ByteArrayInputStream(fileBytes)); } catch {}
    }
    // 最终兜底：UTF-8文本
    return new String(fileBytes, StandardCharsets.UTF_8);
}
```

#### 3.2.3 DOCX递归解析（结构化标签处理）

DOCX本质是ZIP包，XML内部有 `w:sdt`（Structured Document Tag）结构化标签，可能嵌套目录、文本框等：

```java
// DocxParser.java（357行）
public List<String> parseToLines(InputStream inputStream) {
    XWPFDocument doc = new XWPFDocument(inputStream);
    List<String> lines = new ArrayList<>();

    // 1. 提取正文段落
    for (XWPFParagraph para : doc.getParagraphs()) {
        String text = para.getText();
        if (text != null && !text.isBlank()) lines.add(text);
    }

    // 2. 提取表格内容
    for (XWPFTable table : doc.getTables()) {
        for (XWPFTableRow row : table.getRows()) {
            for (XWPFTableCell cell : row.getTableCells()) {
                lines.add(cell.getText());
            }
        }
    }

    // 3. 递归提取 w:sdt 结构化标签（核心难点）
    extractSdtTextRecursive(doc.getDocument(), lines);

    // 4. 提取页眉页脚
    for (XWPFHeader header : doc.getHeaderList()) {
        lines.addAll(extractHeaderText(header));
    }
    for (XWPFFooter footer : doc.getFooterList()) {
        lines.addAll(extractFooterText(footer));
    }

    return lines;
}

// DOM递归遍历，查找w:sdt元素
private void extractSdtTextRecursive(CTDocument1 document, List<String> lines) {
    traverseSdtFromNode(document.getBody().getDomNode(), lines);
}

private void traverseSdtFromNode(Node node, List<String> lines) {
    NodeList children = node.getChildNodes();
    for (int i = 0; i < children.getLength(); i++) {
        Node child = children.item(i);
        if ("w:sdt".equals(child.getLocalName())) {
            // 找到SDT标签，提取文本
            extractTextFromSdtNode(child, lines);
        } else {
            // 不是SDT，继续递归
            traverseSdtFromNode(child, lines);
        }
    }
}

// 从SDT节点提取文本，处理超链接字段
private void extractTextFromSdtNode(Node sdtNode, List<String> lines) {
    if (containsHyperlinkField(sdtNode)) {
        // Word目录中的超链接 → 特殊处理
        extractTextFromHyperlinkPara(sdtNode, lines);
    } else {
        // 普通SDT → 递归收集文本
        collectTextFromNode(sdtNode, lines);
    }
}
```

### 3.3 项目应用场景

数据集可能以ZIP包形式上传，ZIP包内包含多个不同格式的文档文件：

```java
// ZipUtil.java
public Map<String, FileInfo> unzip(byte[] zipBytes) {
    ZipInputStream zis = new ZipInputStream(new ByteArrayInputStream(zipBytes));
    ZipEntry entry;
    while ((entry = zis.getNextEntry()) != null) {
```

### 3.4 为什么要这样处理

**问题**：
1. 用户上传的文件可能格式不规范（扩展名和实际格式不匹配）
2. DOCX文件中的目录结构化标签，普通解析器无法正确提取
3. 不同编码的中文文档（UTF-8/GBK）处理方式不同

**解决方案**：

- 多级回退链保证格式容错性

## 四、并发控制

### 4.1 背景

项目中存在高并发场景：

1. **数据集下载去重**：同一秒内多个请求下载同一个数据集，不应该重复下载
2. **外部API限流**：调用外部Python调度引擎，并发太高会被限流
3. **失败任务重试**：失败任务需要定时重试，但不能多实例同时重试

### 4.2 原理

#### 4.2.1 ConcurrentHashMap下载去重

```java
// XhaiServiceImpl.java
private final ConcurrentHashMap<String, CompletableFuture<byte[]>> downloadingCache =
    new ConcurrentHashMap<>();

public byte[] downloadDatasetZip(String datasetCode, HttpServletRequest httpRequest) {
    // 第一层：检查是否已有下载中的任务
    CompletableFuture<byte[]> existingFuture = downloadingCache.get(datasetCode);
    if (existingFuture != null) {
        log.info("数据集{}正在下载中，等待复用结果", datasetCode);
        try {
            return existingFuture.join();  // 等待已有下载完成
        } catch (CompletionException e) {
            downloadingCache.remove(datasetCode);
            return downloadDatasetZip(datasetCode, httpRequest);  // 失败了重试
        }
    }

    // 第二层：创建新的下载Future
    CompletableFuture<byte[]> newFuture = new CompletableFuture<>();
    CompletableFuture<byte[]> race = downloadingCache.putIfAbsent(datasetCode, newFuture);
    if (race != null) {
        return race.join();  // 另一个线程抢先创建了，join等它
    }

    try {
        byte[] result = doDownloadDatasetZip(datasetCode, httpRequest);
        newFuture.complete(result);       // 下载完成，通知所有等待者
        return result;
    } catch (Throwable e) {
        newFuture.completeExceptionally(e); // 失败，通知所有等待者
        throw e;
    } finally {
        downloadingCache.remove(datasetCode);  // 清理缓存
    }
}
```

**ConcurrentHashMap线程安全原理（Java 8+）**：
- 读操作无锁：Node的 `val` 和 `next` 用 `volatile` 修饰，保证可见性
- 写操作在桶为空时用 **CAS 无锁写入**，桶不为空时用 **synchronized 锁住头节点**（锁粒度缩小到单个桶）
- `putIfAbsent` 内部是CAS原子操作，不会有两个线程同时写入同一个key
- `get` 是 volatile 读，不会被写入阻塞

#### 4.2.2 Semaphore限流

```java
// CleaningDiffCacheServiceImpl.java
private final Semaphore rateLimiter = new Semaphore(1);

public CleaningDiffResult calculateDiffAsync(...) {
    boolean acquired = false;
    try {
        rateLimiter.acquire();  // 获取许可，没获取到会阻塞
        acquired = true;
        log.info("获取到执行权限，开始计算diff");

        // ... 异步计算逻辑

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    } finally {
        if (acquired) {
            rateLimiter.release();  // 释放许可，在finally里保证一定释放
        }
    }
}
```

**Semaphore原理**：
- 内部维护一个 `permits` 计数
- `acquire()` 尝试减少计数，如果计数为0则阻塞
- `release()` 增加计数，唤醒等待的线程
- `acquire()` / `release()` 必须成对调用，建议放在 `try-finally` 中保证释放

#### 4.2.3 指数退避重试

```java
// CleaningDiffCacheServiceImpl.java
// 指数退避：30s * 2^retryCount
// 第1次：30秒后，第2次：60秒后，第3次：120秒后
long delaySeconds = 30L * (1L << retryCount);
nextRetryTime = LocalDateTime.now().plusSeconds(delaySeconds);
```

### 4.3 项目应用场景

1. **数据集下载**：用户A和用户B同时下载同一个数据集（同一秒内），第二个请求等待第一个下载完成的结果即可
2. **Diff异步计算**：Diff计算调用外部API，最多同时1个计算任务在执行，防止被限流
3. **失败任务重试**：定时扫描失败任务，按指数退避重试，重试超过3次仍失败则放弃

### 4.4 为什么要这样处理

**下载去重问题**：同一数据集被100个并发请求下载，如果每个都独立下载，会浪费99次带宽和计算资源。`ConcurrentHashMap + CompletableFuture` 实现"一次下载，多个请求共享结果"。

**Semaphore限流问题**：外部API有并发限制，超出限制会被拒绝。用 `Semaphore(1)` 控制单实例内的并发数，保证不超限。

**指数退避问题**：如果重试间隔固定（如总是5秒），在外部服务故障时，重试请求会持续打服务造成雪崩。指数退避让重试间隔逐渐拉长，给下游恢复时间。

### 4.5 已解决的问题

1. **去重 + 错误处理**：一个下载失败不会影响其他等待者，`completeExceptionally` 正确传递异常给所有等待的线程
2. **信号量泄漏**：`acquire()` / `release()` 放在 `try-finally` 中，保证异常情况下也能释放
3. **submitting状态卡死**：如果提交过程中崩溃，`submitting=true` 会永远卡住；设计了10分钟超时强制清理

### 4.6 优化的地方

1. **Semaphore改为可配置**：`Semaphore(1)` 写死了，当前场景够用，但如果要提升并发度需要可配置
2. **带超时的acquire**：当前 `acquire()` 无限等待，应该加超时，超时后走降级逻辑
3. **重试队列持久化**：当前失败任务放内存，应用重启后丢失；应该持久化到数据库

## 五、分布式锁+降级

### 5.1 背景

多实例部署时，定时任务（如失败任务重试扫描）在多个实例上同时运行，会导致重复处理。用Redis实现分布式锁，确保同一时刻只有一个实例执行。

同时，Redis作为缓存层，如果Redis不可用，需要有降级策略保证核心功能不受影响。

### 5.2 原理

#### 5.2.1 Redis SETNX分布式锁

```java
// CleaningDiffCacheServiceImpl.java
private static final String RETRY_TASK_LOCK_KEY = "cache:retry:lock";

private boolean tryLock() {
    Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(RETRY_TASK_LOCK_KEY, "locked", 30, TimeUnit.SECONDS);
    return Boolean.TRUE.equals(acquired);
}

private void unlock() {
    redisTemplate.delete(RETRY_TASK_LOCK_KEY);
}

// 使用
public void scanAndRetryFailedTasks() {
    if (!tryLock()) {
        log.info("未获取到锁，跳过本次重试扫描");
        return;
    }
    try {
        // 执行重试逻辑...
    } finally {
        unlock();
    }
}
```

**SETNX原理**：
- `SET key value NX PX milliseconds`：原子操作，当key不存在时才设置，返回true表示获取锁成功
- 设置TTL防止死锁（实例崩溃后锁能自动释放）
- NX保证原子性，不会出现两个实例同时获取到锁的情况

#### 5.2.2 缓存降级策略

```java
// 缓存不存在 → 触发异步计算 + 返回实时结果（不阻塞）
if (cachedResult == null) {
    triggerAsyncCalculation(taskId, operatorCode);
    return documentDiffService.compareByTaskNode(request);  // 降级到实时计算
}

// 缓存正在计算中 → 也返回实时结果
case COMPUTING, PENDING -> {
    return documentDiffService.compareByTaskNode(request);
}
```

### 5.3 项目应用场景

1. **失败任务重试扫描**：定时任务每分钟扫描失败任务，多实例部署时只有获取到锁的实例执行扫描
2. **Diff缓存降级**：缓存不存在或正在计算时，返回实时计算结果，不阻塞用户请求

### 5.4 为什么要这样处理

**分布式锁问题**：定时任务在多实例上同时运行会导致重复处理、数据不一致。用Redis SETNX实现分布式锁简单有效。

**缓存降级问题**：缓存是性能优化不是强依赖，Redis不可用时应该降级到实时计算，保证核心业务不中断。

### 5.5 已解决的问题

1. **锁自动过期**：设置30秒TTL，如果实例崩溃，锁能自动释放，不会永久阻塞其他实例
2. **降级策略**：缓存不可用时返回实时结果，用户感知到的延迟增加但功能可用
3. **信号量泄漏配合分布式锁**：单实例内的 `Semaphore` 限流 + 多实例间的Redis分布式锁，形成双重保护

### 5.6 优化的地方

1. **锁的value应该用UUID**：当前value是固定字符串 `"locked"`，释放锁时直接delete可能误删其他实例的锁。应该用UUID作为value，释放时用Lua脚本原子性比较value再删除
2. **看门狗续期**：如果任务执行超过30秒，锁会过期被其他实例获取。可以用Redisson的看门狗机制自动续期
3. **Redis不可用检测**：当前降级是隐式的，可以显式监控Redis连接状态，提前告警

## 六、数据一致性

### 6.1 背景

数据清洗任务涉及大量数据写入（可能几十万条差异行），需要保证数据一致性：
- 多表写入要么全部成功要么全部回滚
- 批量操作需要高性能，不能一条条INSERT
- 异步线程需要持有主线程的上下文（如Cookie）

### 6.2 原理

#### 6.2.1 MyBatis BATCH批量写入

```java
// CleaningDiffLineRepo.java
public void batchInsert(Long resultId, List<CleaningDiffLine> lines) {
    if (lines == null || lines.isEmpty()) return;

    // 开启BATCH模式的SqlSession，手动控制事务
    try (SqlSession sqlSession = sqlSessionFactory.openSession(ExecutorType.BATCH, false)) {
        CleaningDiffLineMapper batchMapper = sqlSession.getMapper(CleaningDiffLineMapper.class);

        try {
            for (CleaningTaskLine line : lines) {
                CleaningDiffLinePO po = converter.entityToPo(line);
                po.setResultId(resultId);
                batchMapper.insert(po);           // 不立即执行，加入批处理队列
            }
            sqlSession.flushStatements();          // 一次性提交所有SQL
            sqlSession.commit();                   // 提交事务
        } catch (Exception e) {
            sqlSession.rollback();                 // 失败回滚
            throw e;
        }
    }
}
```

**BATCH模式原理**：
- `openSession(ExecutorType.BATCH)` 开启批处理模式
- `insert()` 不是立即执行，而是把SQL和参数加入批处理队列
- `flushStatements()` 一次性发送所有SQL到数据库，减少网络往返
- 比普通INSERT性能提升10倍以上

#### 6.2.2 ThreadLocal异步上下文穿透

```java
// CookieContextHolder.java
public class CookieContextHolder {
    private static final ThreadLocal<String> COOKIE_HOLDER = new ThreadLocal<>();

    public static void setCookie(String cookie) { COOKIE_HOLDER.set(cookie); }
    public static String getCookie() { return COOKIE_HOLDER.get(); }
    public static void clear() { COOKIE_HOLDER.remove(); }  // 必须清理，防止内存泄漏
}
```

**使用场景**：主线程提取Cookie存入ThreadLocal，异步线程通过 `getCookie()` 获取。

**内存泄漏原因**：ThreadLocal存在Thread的 `ThreadLocalMap` 里，key是 `WeakReference`，value是强引用。如果线程不销毁（线程池场景），value不会被GC。所以用完必须 `remove()`。

#### 6.2.3 @Transactional事务保证

```java
@Transactional(rollbackFor = Exception.class)
public void createCleaningTask(...) { ... }

@Transactional(rollbackFor = Exception.class)
public void createTask(...) { ... }
```

- Spring事务默认只回滚 RuntimeException 和 Error
- `rollbackFor = Exception.class` 确保检查型异常也回滚

### 6.3 项目应用场景

1. **批量写入差异行**：数据清洗后产生几十万条差异行数据，BATCH模式批量写入保证性能和一致性
2. **异步任务Cookie穿透**：下载数据集的异步任务需要在子线程中携带Cookie调外部API
3. **多表原子操作**：创建清洗任务时需要同时写任务表和节点表，用事务保证原子性

### 6.4 为什么要这样处理

**BATCH写入问题**：如果一条条INSERT，几十万条数据需要几十万次网络往返，性能极差。BATCH模式只编译一次SQL，所有参数攒内存，最后一次性发送，性能提升10倍以上。

**ThreadLocal问题**：Tomcat的Request对象在响应返回后会被recycle，异步线程中直接获取会报 "request object has been recycled" 异常。用ThreadLocal在主线程提取，异步线程获取，解决上下文传递问题。

### 6.5 已解决的问题

1. **事务边界明确**：BATCH模式下，手动控制 `commit()` / `rollback()`，确保事务正确
2. **ThreadLocal清理**：所有使用ThreadLocal的地方都在finally中调用 `clear()`，防止内存泄漏
3. **异步异常传递**：下载失败时 `completeExceptionally` 正确传递异常给所有等待的线程

### 6.6 优化的地方

1. **大批量数据分批处理**：BATCH模式把数据全放内存，数据量特别大时可能内存溢出；应该分批（如每1000条一批）处理
2. **异步线程池隔离**：当前异步线程池和业务线程池混用，应该隔离，避免相互影响
3. **事务传播行为**：当前用的默认 `REQUIRED`，如果异步方法调事务方法会丢失事务；应该显式指定 `REQUIRES_NEW`

## 七、缓存体系

### 7.1 背景

数据集列表查询调用外部API，频率高、数据变化不频繁。如果每次都调外部API，网络开销大、响应慢。需要本地缓存减少外部调用。

### 7.2 原理

#### 7.2.1 本地ConcurrentHashMap缓存

```java
// DatasetServiceImpl.java
private static final long CACHE_EXPIRE_MS = 5 * 60 * 1000;  // 5分钟过期
private final Map<String, CacheEntry> datasetCache = new ConcurrentHashMap<>();

private static class CacheEntry {
    final List<DatasetInfo> datasets;
    final long timestamp;
}

private List<DatasetInfo> getOrFetchDatasets(String cacheKey, ...) {
    CacheEntry cacheEntry = datasetCache.get(cacheKey);

    // 缓存有效 → 直接返回
    if (cacheEntry != null && !isCacheExpired(cacheEntry)) {
        log.info("使用缓存数据，数据量：{}", cacheEntry.datasets.size());
        return cacheEntry.datasets;
    }

    // 缓存过期/不存在 → 重新获取并更新缓存
    List<DatasetInfo> freshDatasets = fetchAllCompleteDatasets(queryDTO, httpRequest);
    datasetCache.put(cacheKey, new CacheEntry(freshDatasets, System.currentTimeMillis()));
    return freshDatasets;
}

private boolean isCacheExpired(CacheEntry cacheEntry) {
    return System.currentTimeMillis() - cacheEntry.timestamp > CACHE_EXPIRE_MS;
}
```

### 7.3 项目应用场景

数据集列表页面加载时，根据用户查询条件生成缓存key，先查本地缓存，命中直接返回；过期或不存在则调外部API获取新数据。

### 7.4 为什么要这样处理

**问题**：外部API调用开销大、响应慢，数据集列表页面频繁访问，每次都调外部API体验差。

**解决方案**：本地 `ConcurrentHashMap` 缓存，5分钟过期，命中直接返回无网络开销。

### 7.5 已解决的问题

1. **缓存过期策略**：用时间戳判断是否过期，过期后触发异步刷新，用户拿到的是旧数据但不影响使用
2. **线程安全**：用 `ConcurrentHashMap` 保证并发安全
3. **缓存穿透**：当前方案查库后直接返回空数据，可能缓存穿透；可以加空值缓存

### 7.6 优化的地方

1. **迁移到Caffeine**：当前用 `ConcurrentHashMap`，适合简单场景。如果缓存条目多、需要LRU淘汰，可以迁移到Caffeine（支持W-TinyLFU算法）
2. **缓存预热**：应用启动时主动加载热点数据，避免冷启动
3. **缓存统计**：当前没有缓存命中率统计，可以加监控指标辅助调优

## 八、服务注册与发现（Nacos / Zookeeper）

### 8.1 整体架构概览

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  服务提供者A  │────▶│   注册中心   │◀────│  服务消费者B  │
│  (Provider) │     │ Nacos / ZK  │     │  (Consumer) │
└─────────────┘     └─────────────┘     └─────────────┘
      │                    │                    │
      │ 1.注册/心跳         │ 2.订阅/监听         │
      ▼                    ▼                    ▼
   启动时               定时心跳              启动时
   注册地址             失败则移除            获取实例列表
```

**核心流程**：
1. **注册**：服务提供者启动时向注册中心注册自己的地址（IP+Port）
2. **心跳**：提供者定时向注册中心发送心跳，证明自己还活着
3. **订阅**：服务消费者启动时订阅服务列表，注册中心推送变更
4. **调用**：消费者从本地缓存的服务列表中选择一个地址发起RPC调用

### 8.2 Zookeeper 注册原理

#### 8.2.1 临时有序节点

ZK 采用**临时有序节点**存储服务实例：

```
/services
  /user-service          （持久化父节点）
    /000001              （临时节点，实例1）
      Data: 192.168.1.10:8080
    /000002              （临时节点，实例2）
      Data: 192.168.1.11:8080
```

**为什么用临时节点？**
- 临时节点的生命周期和客户端会话绑定
- 客户端断开连接 → 节点自动删除 → 其他服务感知到实例下线
- 不需要额外的健康检查机制

**为什么用有序节点？**
- ZK 自动为节点名加序号（000001, 000002...）
- 保证节点名的唯一性

| **会话依赖** | 网络闪断可能导致临时节点被误删 |
| **不适合大规模服务** | ZK设计目标是分布式锁，不是服务发现，千级服务实例时性能下降 |
| **无健康检查** | 依赖临时节点机制，没有主动探活的健康检查 |

### 8.3 Nacos 注册原理

#### 8.3.1 两种实例模式

Nacos 支持两种模式：**临时实例**（默认）和**永久实例**：

```
临时实例（ephemeral=true）
  ├── 心跳检测
  ├── 超时30秒 → 标记 unhealthy
  └── 超时90秒 → 移除实例

永久实例（ephemeral=false）
  ├── 主动注册，不主动下线
  └── 需要主动发送 Delete 请求取消注册
```

**与 ZK 的核心区别**：
- ZK 用临时节点 + 会话机制，被动检测下线
- Nacos 用**主动心跳检测**，有后台线程轮询检查实例健康状态

#### 8.3.2 Nacos 核心代码实现

```java
// 服务提供者注册
@NacosInjected
private NacosNamingService namingService;

public void register(String host, int port) throws NacosException {
    Instance instance = new Instance();
    instance.setIp(host);
    instance.setPort(port);
    instance.setHealthy(true);    // 健康状态
    instance.setWeight(1.0);      // 负载均衡权重
    instance.getMetadata().put("version", "1.0");

    // 注册临时实例（ephemeral=true）
    namingService.registerInstance("user-service", instance);

    // Nacos 客户端会自动心跳，不需要手动维护
}
```

```java
// 服务消费者订阅 + 发现
public void subscribeAndCall() throws NacosException {
    // 订阅服务，实例变更时自动回调
    namingService.subscribe("user-service", event -> {
        List<Instance> instances = namingService.selectInstances("user-service", true);
        updateLoadBalancer(instances);
    });

    // 直接获取健康实例
    Instance instance = namingService.selectOneHealthyInstance("user-service");
    String url = "http://" + instance.getIp() + ":" + instance.getPort() + "/api";
}
```

#### 8.3.3 Nacos 客户端心跳机制

```
Provider 启动
    │
    ├──▶ HTTP PUT /v1/ns/instance
    │      注册到 Nacos Server
    │
    └──▶ 客户端自动心跳（每5秒一次）
             │
             ▼
         HTTP PUT /v1/ns/instance/beat
         更新 lastBeat 时间戳
             │
             ▼
         Server 后台任务（每10秒一次）
             │
             ├──▶ 检查 lastBeat
             ├──▶ 超过 30 秒 → 标记 unhealthy
             └──▶ 超过 90 秒 → 移除实例
```

### 8.4 服务调用通信细节

#### 8.4.1 客户端负载均衡（Ribbon / OpenFeign）

```
消费者                         注册中心                    提供者
  │                               │                       │
  │  订阅服务列表                   │                       │
  │ ─────────────────────────────▶ │                       │
  │                               │                       │
  │  获取实例列表                   │                       │
  │ ◀───────────────────────────── │                       │
  │  [实例1, 实例2, 实例3]          │                       │
  │                               │                       │
  │  本地缓存                       │                       │
  │ ──────────────────────────────▶  负载均衡选择实例1       │
  │                               │                       │
  │  HTTP 调用                                             │
  │ ════════════════════════════════════════════════════▶│
  │     GET /api/user/123                                  │
  │ ◀═══════════════════════════════════════════════════│
```

**特点**：
- 消费者从注册中心获取实例列表，缓存在本地
- 负载均衡逻辑在消费者端执行（Ribbon 客户端负载均衡）
- 注册中心变更时，通过订阅机制推送更新到消费者本地缓存

#### 8.4.2 OpenFeign 调用链路

```java
// 1. 定义 Feign 客户端接口
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/api/user/{id}")
    User getUser(@PathVariable("id") Long id);
}

// 2. 消费者调用
@RestController
public class OrderController {
    @Autowired
    private UserClient userClient;

    public Order getOrder(Long id) {
        // 内部流程：
        // 1. Ribbon 从 Nacos 获取实例列表（本地缓存）
        // 2. Ribbon 负载均衡选择一个实例
        // 3. Feign 生成请求 URL 并发起 HTTP 调用
        User user = userClient.getUser(id);
        return new Order(id, user);
    }
}
```

**内部流程**：
```
1. OpenFeign 拦截器拦截请求
       │
2. RibbonLoadBalancer 从本地缓存获取 user-service 实例列表
       │
3. RibbonLoadBalancer 根据负载策略选择实例（假设 192.168.1.11:8080）
       │
4. Feign 生成请求 URL → http://192.168.1.11:8080/api/user/1
       │
5. HTTP Client 发起调用
       │
6. 成功 → 返回 Response
   失败 → Ribbon 重试同实例或换实例重试
```

#### 8.4.3 两种调用模式对比

| 维度 | 客户端负载均衡（Ribbon/Feign） | 服务端负载均衡（Nginx/LB） |
|------|------------------------------|--------------------------|
| **负载均衡位置** | 消费者端 | 服务端 |
| **消费者是否知道实际地址** | 知道（从注册中心拉取） | 不知道（Nginx转发） |
| **注册中心压力** | 消费者定时拉取 | 服务端定期同步 |
| **灵活性** | 高（可自定义路由规则） | 低 |
| **复杂度** | 较高 | 较低 |

### 8.5 Nacos vs Zookeeper 对比

| 维度 | Zookeeper | Nacos |
|------|-----------|-------|
| **一致性协议** | ZAB协议，强一致 | CP + AP 可切换 |
| **健康检查** | 被动（会话断则节点删） | 主动心跳探测 |
| **临时实例** | 只能用临时 | 临时 + 永久都支持 |
| **服务容量** | 千级实例 | 万级实例 |
| **批量注册** | 不支持 | 支持批量注册 |
| **配置管理** | 不支持 | 支持配置管理 |
| **界面** | 无 | 有 Web 管理界面 |
| **选主机制** | 自带 | 不支持（需配合其他组件） |

### 8.6 服务下线与优雅退出一致性问题

```
场景：user-service 要缩容下线 2 台机器

方案一：正常优雅下线（推荐）
  1. 关闭实例监听（Nacos 控制台或 API）
  2. 等待流量切走（约 30 秒心跳时间）
  3. 关闭服务进程

方案二：强制下线（不推荐）
  1. 直接 kill 服务进程
  2. Nacos 心跳超时 → 30秒后标记 unhealthy
  3. Nacos 心跳超时 → 90秒后移除实例
  4. 已发起的请求 → 失败
```

**优雅下线代码**：
```java
@PreDestroy
public void deregister() throws NacosException {
    // 1. 从 Nacos 注销实例
    namingService.deregisterInstance("user-service", instance);

    // 2. 等待已有请求处理完
    Thread.sleep(3000);  // 等待3秒，流量切走

    // 3. 关闭服务
}
```

### 8.7 如果注册中心挂了，服务还能调用吗

**能调用，但有限制**：

```
注册中心挂了
    │
    ├──▶ 消费者本地已缓存实例列表
    │     → 可以继续用缓存的地址发起调用
    │
    ├──▶ 新实例上线 → 感知不到
    │
    └──▶ 旧实例下线 → 感知不到
              → 调用到已下线实例会失败
                  → Ribbon 重试机制兜底
```

**解决思路**：
1. 消费者本地缓存实例列表
2. 注册中心挂了用本地缓存
3. 调用失败时 Ribbon 重试（换实例重试）
4. 多注册中心集群部署提高可用性

### 8.8 为什么要用注册中心

**直连的问题**：
- 服务地址硬编码，改IP要改代码
- 不知道哪些实例还活着
- 负载均衡要自己实现
- 扩缩容要手动改配置

**注册中心的价值**：
- 服务地址自动发现
- 健康检查自动感知
- 负载均衡自动协调
- 扩缩容零配置

## 九、综合技术问题准备

### 9.1 登录拦截和用户信息链路

**完整链路**：
```
HTTP请求 → Filter/Interceptor校验Token
        → 解析Token获取用户ID/角色
        → 存入ThreadLocal或RequestContext
        → Controller正常获取用户信息
        → Service层使用
        → 异步场景：主线程CookieContextHolder.setCookie()
        → 异步线程CookieContextHolder.getCookie()
        → 执行完CookieContextHolder.clear()清理
```

**为什么异步线程拿不到Request**：Tomcat在响应返回后 recycle Request 对象，异步线程执行时可能已被回收

**ThreadLocal内存泄漏**：线程池中的线程会复用，不用时必须 `remove()`，否则下一个任务可能拿到上一个用户的上下文

### 9.2 技术方案对比

| 场景 | 当前方案 | 可选方案 | 优点 | 缺点 |
|------|----------|----------|------|------|
| 分布式锁 | Redis SETNX | Redisson | 简单、性能好 | 无续期、可能误删 |
| 分布式锁 | | ZooKeeper | 强一致 | 性能差、重量级 |
| 本地缓存 | ConcurrentHashMap | Caffeine | 零依赖、速度快 | 无淘汰策略 |
| 本地缓存 | | Redis | 分布式共享 | 有网络开销 |

### 9.4 服务注册与发现

**问：请介绍一下服务注册与发现的过程**

> 服务注册发现分为三个阶段：**注册阶段**——服务提供者启动时通过 HTTP 或 SDK 将自己的地址注册到注册中心，Nacos 支持临时实例和永久实例，临时实例通过心跳维持。**心跳阶段**——Nacos 客户端每5秒自动发送一次心跳，注册中心收到后更新实例的 `lastBeat` 时间戳，超过30秒没心跳标记不健康，超过90秒则移除。**发现阶段**——服务消费者启动时订阅服务列表，注册中心推送变更到消费者本地缓存。消费者调用时从本地缓存获取实例列表，通过 Ribbon 做负载均衡选择地址发起 HTTP 调用。实例变更时注册中心通过 Watch 机制主动推送更新。

**问：Nacos 和 Zookeeper 有什么区别**

> 核心区别有三点：**第一，健康检查机制不同**。ZK 靠临时节点 + 会话机制，断连就删节点，是被动的。Nacos 有主动心跳探测，可以配置健康检查规则，更灵活。**第二，一致性保证不同**。ZK 强一致（ZAB协议），只支持 CP。Nacos 默认 AP，可以通过配置切换 CP，适合注册中心优先可用性的场景。**第三，规模不同**。ZK 设计目标是分布式协调，服务发现不是它的强项，千级实例性能开始下降。Nacos 原生支持服务发现和配置管理，万级实例没问题，而且有 Web 管理界面。

**问：如果注册中心挂了，服务还能调用吗**

> 能，但有限制。消费者本地缓存了服务实例列表，注册中心挂了可以继续用缓存的地址发起调用。但新实例上线、旧实例下线都感知不到了，调用到已下线实例会失败。解决思路是客户端本地缓存 + 重试机制 + 多注册中心集群部署提高可用性。

### 9.5 技术选型：注册中心选 Nacos 还是 Zookeeper

| 维度 | Zookeeper | Nacos | 推荐场景 |
|------|-----------|-------|----------|
| 一致性 | ZAB强一致（CP） | CP + AP 可切换 | 注册中心优先选AP |
| 健康检查 | 被动会话检测 | 主动心跳探测 | 需要灵活健康检查选Nacos |
| 规模 | 千级实例 | 万级实例 | 大规模服务选Nacos |
| 配置管理 | 不支持 | 支持 | 需要配置中心选Nacos |
| 选主/分布式锁 | 自带 | 需配合其他组件 | 纯协调场景选ZK |
| 界面 | 无 | 有 | 需要管理界面选Nacos |

## 十、面试回答模板

### 10.1 DSL工作流引擎

**问：请介绍一下你的DSL工作流引擎**

> 我们的工作流引擎分三层：第一层是 `WorkflowBuildService` 负责参数校验和节点配置转换；第二层是 `SaveWorkflowRequestFactory` 工厂类，根据算子枚举类型动态组装完整的JSON配置（包含节点定义、连线、算法配置等）；第三层是外部Python调度引擎实际执行。算子系统用155个枚举常量管理元数据，新增算子只需要在枚举加一条记录，不需要改工厂代码，扩展成本降低90%。

### 10.2 崩溃恢复

**问：任务执行过程中服务崩溃了怎么处理**

> 有崩溃恢复机制。应用重启时，`TaskRecoveryService` 扫描所有RUNNING状态的任务，对每个任务做三层判断：1）如果任务刚启动3分钟内跳过，避免干扰正常执行；2）如果从未提交到外部平台，重新提交整个任务；3）如果已提交过，查询外部平台的真实状态，找到断点位置（有taskInstanceId但没有dataSetCode的节点），然后从断点继续执行后续节点。状态都持久化到数据库，增量恢复不需要重新执行已完成的节点。

### 10.3 ConcurrentHashMap线程安全

**问：ConcurrentHashMap是如何实现线程安全的**

> Java 8+的ConcurrentHashMap用CAS + synchronized实现。读操作完全无锁，因为Node的val和next用volatile修饰，保证可见性。写操作分情况：桶为空时用CAS无锁写入，桶不为空时用synchronized锁住头节点，锁粒度是单个桶。计数用CounterCell分散，避免竞争。和Hashtable相比（全局一把锁），ConcurrentHashMap的并发度大大提高。

### 10.4 缓存降级

**问：Redis不可用了怎么办**

> 我们有缓存降级策略。缓存的作用是性能优化，不是强依赖。当缓存不存在或正在计算时，触发后台异步计算，同时直接返回实时计算结果。用户感知到的延迟增加但功能可用。这样设计的好处是Redis故障时不影响核心业务。当然我们也有监控，Redis长时间不可用时会告警运维处理。

### 10.5 线程池配置

**问：你们的线程池是怎么配置的**

> 我们的工作流执行线程池按IO密集型配置：核心线程数是CPU核数*2（因为主要在等外部API响应），最大100个线程。队列容量200，拒绝策略用CallerRunsPolicy（队列满时由提交任务的线程自己执行），这样既不丢任务又能自然降低提交速度。定时扫描任务用分布式锁保证单实例执行。

## 十二、外部模型配置常量（ModelConstant）

### 12.1 背景

项目中需要对接多种外部AI模型服务（文本处理、图像检测、音频转写等），每种模型都有独立的HTTP调用配置（URL、请求方式、请求参数、响应解析规则等）。如果这些配置散落在各处，修改维护困难，需要统一管理。

### 12.2 原理

#### 12.2.1 配置结构

每个模型的配置都是一个JSON字符串，包含以下关键字段：

```java
public static final String TEXT_TRANSLATE = "{\n" +
    "    \"modelName\": \"text-translate\",\n" +           // 模型名称
    "    \"modelType\": \"HTTP\",\n" +                      // 模型类型：HTTP调用
    "    \"modelConfig\": {\n" +
    "        \"url\": \"http://127.0.0.1:8080/text_translate\",\n" +  // 请求地址
    "        \"method\": \"POST\",\n" +                     // 请求方法
    "        \"header\": {},\n" +                          // 请求头
    "        \"body\": [\n" +                               // JSON请求体
    "            {\n" +
    "                \"data_type\": \"text\",\n" +
    "                \"data\": \"${data}\",\n" +             // 模板变量：运行时替换
    "                \"tgt_lang\": \"${tgt_lang}\"\n" +
    "            }\n" +
    "        ],\n" +
    "        \"files\": null,\n" +                         // 文件上传
    "        \"form_data\": null,\n" +                     // 表单数据
    "        \"response_paths\": [\n" +                    // 响应解析路径
    "            {\n" +
    "                \"property_name\": \"result\",\n" +
    "                \"property_type\": \"OBJECT\",\n" +
    "                \"property_pointer\": \"$.result\",\n" +  // JSONPath表达式
    "                \"property_cname\": \"result\"\n" +
    "            }\n" +
    "        ]\n" +
    "    }\n" +
    "}";
```

#### 12.2.2 模板变量替换机制

配置中使用 `${xxx}` 作为模板变量占位符，运行时通过模板引擎替换为实际值：

| 模板变量 | 说明 | 示例值 |
|---------|------|--------|
| `${data}` | 请求数据 | Base64编码的文件内容或文本 |
| `${tgt_lang}` | 目标语言 | "en", "ja", "ko" |
| `${target_style}` | 目标风格 | "formal", "casual" |
| `${temperature}` | 采样温度 | 0.0 - 2.0 |
| `${data_binary}` | 二进制文件数据 | 文件的二进制内容 |
| `${return_text_content}` | 是否返回文本内容 | "true", "false" |

#### 12.2.3 三种请求模式

```java
// 模式一：JSON Body 请求
"body": [{"data_type": "text", "data": "${data}"}]
// Content-Type: application/json

// 模式二：表单+文件上传
"files": {"file": "${data_binary}"}
"form_data": {"temperature": "${temperature}"}
// Content-Type: multipart/form-data

// 模式三：纯文件上传
"files": {"file": "${data_binary}"}
"form_data": null
// Content-Type: multipart/form-data
```

#### 12.2.4 响应路径解析（JSONPath）

通过 `property_pointer` 字段指定JSONPath表达式，从响应中提取结果：

```java
// 响应结构：
// {"status": 0, "result": [{"text": "hello"}], "message": ""}

// property_pointer: "$.result"
// → 提取 result 字段

// property_pointer: "$.result[0].output.image"
// → 提取 result 数组第一个元素的 output.image 字段
```

### 12.3 项目应用场景

项目中接入的模型分为几大类：

#### 12.3.1 文本处理模型（16个）

| 模型常量 | 功能 | 请求方式 |
|----------|------|----------|
| `TEXT_TRANSLATE` | 文本翻译 | JSON Body |
| `STYLE_TRANSFER` | 风格迁移 | 表单+文件 |
| `ADJUST_TEXT_TEST` | 文本调整 | 表单+文件 |
| `PARAPHRASE` | 文本改写 | 表单+文件 |
| `SENTENCE_SPLIT` | 句子切分 | 表单+文件 |
| `SENTENCE_MERGE` | 句子合并 | 表单+文件 |
| `TYPO_INJECTION` | 错别字注入 | 表单+文件 |
| `PINYIN_REPLACEMENT` | 拼音替换 | 表单+文件 |
| `REPETITION_INJECTION` | 重复注入 | 表单+文件 |

## 十三、MySQL数据库知识重点

### 13.1 B+树索引原理

#### 13.1.1 为什么用B+树而不是B树

| 对比维度 | B树 | B+树（InnoDB采用） |
|----------|-----|-------------------|
| 非叶子节点 | 存储key和data | 只存储key |
| 叶子节点 | 存储data | 存储所有data，叶子链表连接 |
| 树高度 | 较高 | 较矮（一个页能存更多key） |
| 范围查询 | 需要回溯 | 叶子链表直接顺序扫描 |
| 磁盘IO | 随机IO多 | 顺序IO多 |

#### 13.1.2 联合索引最左前缀原则

```sql
CREATE INDEX idx_name ON table(a, b, c);
```

**生效情况**：

| 查询条件 | 走索引情况 |
|----------|-----------|
| `a = 1` | ✅ a列走索引 |
| `a = 1 AND b = 2` | ✅ a+b列走索引 |
| `a = 1 AND b = 2 AND c = 3` | ✅ a+b+c列走索引 |
| `a > 1 AND b = 2` | ⚠️ a列走索引，b列无法利用 |
| `b = 2 AND c = 3` | ❌ 不走索引（跳过a列） |
| `a LIKE '%xxx'` | ❌ 不走索引（前置通配符） |

**a>1 AND b=1 为什么只有a列走索引**：

```
索引(a,b)的B+树结构（按a排序，a相同再按b排序）：
(a=1, b=1) → (a=1, b=2) → (a=2, b=1) → (a=2, b=2) → (a=3, b=1) → (a=3, b=2)

a>1 扫描范围：a=2 和 a=3 的全部记录
此时 b 列的顺序在 a 的范围查询后被"打断"了：
  a=2 时 b=1,2,3
  a=3 时 b=1,2,3
b=1 的记录分散在不同的 a 值下，不是连续的
所以 b=1 无法通过索引树直接定位，只能在扫描过程中逐行过滤
```

#### 13.1.3 索引失效场景

```sql
-- 场景1：函数计算
WHERE YEAR(create_time) = 2026  -- ❌ YEAR()导致索引失效
WHERE create_time >= '2026-01-01'  -- ✅ 可以走索引

-- 场景2：类型转换
WHERE phone = 13800138000  -- phone是varchar，数字比较导致类型转换
WHERE phone = '13800138000'  -- ✅ 字符串比较

-- 场景3：模糊查询前置通配符
WHERE name LIKE '%张%'  -- ❌ 前置%无法使用索引
WHERE name LIKE '张%'  -- ✅ 可以使用索引

-- 场景4：OR连接
WHERE a = 1 OR b = 2  -- ❌ OR可能不走索引（除非两列都有独立索引）
WHERE a = 1 UNION ALL SELECT * FROM table WHERE b = 2  -- ✅ 改为UNION

-- 场景5：IS NULL / IS NOT NULL
WHERE col IS NULL  -- ⚠️ 可能不走索引（取决于数据分布）
```

### 13.2 事务隔离级别

MySQL默认 `REPEATABLE READ`，通过 MVCC（多版本并发控制）实现：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| READ UNCOMMITTED | ✅ 可能 | ✅ 可能 | ✅ 可能 |
| READ COMMITTED | ❌ 不可能 | ✅ 可能 | ✅ 可能 |
| REPEATABLE READ | ❌ 不可能 | ❌ 不可能 | ⚠️ 可能 |
| SERIALIZABLE | ❌ 不可能 | ❌ 不可能 | ❌ 不可能 |

**MVCC原理**：
- 每行数据有两个隐藏列：`CREATE_VERSION` 和 `DELETE_VERSION`
- 读取数据时，只读取 `CREATE_VERSION <= 当前事务ID AND (DELETE_VERSION > 当前事务ID OR DELETE_VERSION 为空)` 的记录
- 保证同一事务内多次读取结果一致

**REPEATABLE READ 下的间隙锁**：
- MySQL 通过间隙锁（Gap Lock）防止幻读
- 对范围查询加锁时，不仅锁住存在的记录，还锁住"间隙"
- `WHERE id > 10` 会锁住 id > 10 的所有间隙，防止新插入

### 13.3 MyBatis BATCH原理

```java
// 普通模式：每条SQL独立执行
INSERT INTO table VALUES (...);  -- 网络往返1
INSERT INTO table VALUES (...);  -- 网络往返2
INSERT INTO table VALUES (...);  -- 网络往返3

// BATCH模式：批量执行
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "a"); ps.addBatch();
ps.setString(1, "b"); ps.addBatch();
ps.setString(1, "c"); ps.addBatch();
ps.executeBatch();  -- 一次性发送所有SQL
```

**性能差异**：
- 普通模式：N条数据 = N次网络往返 + N次SQL解析 + N次事务提交
- BATCH模式：N条数据 = 1次网络往返 + 1次SQL解析 + 1次事务提交
- 性能提升10倍以上

### 13.4 索引设计原则

1. **区分度高的列放前面**：`WHERE status = 1` 如果 status 只有 0/1 两种值，区分度低，不适合建单列索引
2. **覆盖索引**：查询的列都在索引中，不需要回表，速度快
3. **不要过度索引**：索引占用空间，更新时维护成本高
4. **联合索引遵循最左前缀**：`INDEX(a,b,c)` 从左到右使用，不要跳过前面的列

### 13.5 面试回答模板

**问：(a, b) 联合索引，a>1 AND b=1 会走索引吗？**

> 会走索引，但只有 a 列走索引，b 列无法利用索引。
>
> 联合索引 (a, b) 的数据是按 a 先排序，a 相同时按 b 排序。`a>1` 是范围查询，MySQL 可以通过索引定位到 a>1 的范围，然后顺序扫描。但此时 b 列的顺序在 a 的范围查询后被"打断"了——b=1 的记录分散在不同的 a 值下，不是连续的，所以 b=1 只能作为额外的过滤条件在扫描过程中逐行判断，不能通过索引树直接定位。
>
> 如果想让 b=1 也走索引，需要调整索引顺序为 (b, a)，或者根据实际业务查询模式重新设计索引。

### 14.2 put 流程详解

```java
public V put(K key, V value) {
    // 1. 计算 key 的 hash 值
    int hash = hash(key);

    // 2. 计算数组下标位置
    int index = (n - 1) & hash;  // 等价于 hash % n，但更快

    // 3. 遍历该位置的链表/红黑树
    for (Node<K,V> e = table[index]; e != null; e = e.next) {
        if (e.hash == hash && (e.key == key || key.equals(e.key))) {
            // 3a. key 已存在 → 更新 value，返回旧值
            V oldValue = e.value;
            e.value = value;
            return oldValue;
        }
    }

    // 4. key 不存在 → 新增节点
    modCount++;          // 修改计数器，用于迭代器快速失败
    addCount(1);         // 更新 size

    // 5. 检查是否需要扩容
    if (++size > threshold) {
        resize();
    }

    // 6. 在链表头部插入新节点（Java 7）
    //    Java 8 是在链表尾部插入
    Node<K,V> newNode = new Node<>(hash, key, value, next);
    table[index] = newNode;

    return null;
}
```

**put 流程图**：

```
put("name", "张三")
       │
       ▼
计算 hash = hash("name")
       │
       ▼
计算 index = (n-1) & hash  →  定位数组下标
       │
       ▼
遍历该位置的链表/红黑树
       │
       ├──▶ 找到相同 key ──▶ 更新 value，返回旧值
       │
       └──▶ 没找到相同 key ──▶ 新增节点
                │
                ▼
          检查是否需要扩容（size > threshold）
                │
                ├──▶ 需要扩容 ──▶ resize() 扩容
                │
                └──▶ 不需要扩容 ──▶ 插入完成
```

### 14.3 hash() 方法计算详解

```java
// HashMap 的 hash 算法（Java 8）
static final int hash(Object key) {
    int h;
    // key.hashCode() 的高低16位异或
    // 目的：让 hash 值更加散列，减少 hash 冲突
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

// 计算数组下标
// n 是数组长度（一定是 2 的幂，如 16, 32, 64...）
// index = hash & (n-1)  等价于  hash % n，但 & 比 % 快
int index = hash & (n - 1);
```

**为什么用高低16位异或**：

```
原始 hashCode(): 00000000 00000000 10101010 11111111

h >>> 16:        00000000 00000000 00000000 10101010
h ^ (h>>>16):    00000000 00000000 10101010 01010101  ← 高低位混合，更散列

& (n-1) 时，高位信息会被丢弃（如 n=16 时只保留低4位）
如果只用原始 hashCode，低位可能全为0（如 "abc" 和 "abd" 可能冲突）
异或后，高位信息混合到低位，保证散列效果
```

### 14.4 扩容机制（resize）

```java
// 扩容条件：size 超过 threshold（threshold = capacity * loadFactor）
// 默认：capacity = 16, loadFactor = 0.75, threshold = 12

// 扩容过程：
// 1. 创建新数组，长度是旧数组的 2 倍
// 2. 将旧数组的元素重新分配到新数组（重新计算 index）

// 扩容后的数组长度：16 → 32 → 64 → 128 ...

// 扩容时的元素重分配：
旧 index = hash & (old_n - 1) = hash & 15  = hash & 1111 (二进制)
新 index = hash & (new_n - 1) = hash & 31  = hash & 11111

// 关键：元素的 index 要么不变，要么增加 old_capacity
// 例如：hash=17 的元素
//   旧 index: 17 & 15 = 1
//   新 index: 17 & 31 = 17  （等于 1 + 16）
// 这就是为什么扩容不需要重新计算所有元素的 hash！
```

### 14.5 线程安全分析

**HashMap 不是线程安全的！**

| 线程安全风险 | 场景 | 结果 |
|-------------|------|------|
| 数据覆盖 | 线程A和B同时put相同key | 后者覆盖前者的值 |
| 死循环 | 并发扩容时，两个线程同时resize | 链表成环，get时死循环 |
| 数据丢失 | 并发put时，链表操作被覆盖 | 新增的元素丢失 |

### 14.6 如何保证线程安全

#### 方案一：Hashtable（不推荐）

```java
// 使用 synchronized 锁住整个方法，并发度极低
public synchronized V put(K key, V value) { ... }
public synchronized V get(Object key) { ... }
```

**问题**：所有操作都竞争同一把锁，高并发下性能差

#### 方案二：Collections.synchronizedMap()（不推荐）

```java
Map<K,V> map = Collections.synchronizedMap(new HashMap<>());
// 内部使用 synchronized 包装每个方法，和 Hashtable 类似
```

#### 方案三：ConcurrentHashMap（推荐）

```java
// Java 7：分段锁，每段一个锁
Segment<K,V>[] segments;
Segment<K,V> s = segments[(hash >>> segmentShift) & segmentMask];
s.lock();

// Java 8+：CAS + synchronized
// 桶为空：CAS 无锁写入
// 桶不为空：synchronized 锁头节点
// 并发度大大提升
```

#### 方案四：ConcurrentHashMap  vs  synchronized + HashMap

| 维度 | Hashtable | synchronized HashMap | ConcurrentHashMap |
|------|-----------|---------------------|-------------------|
| 并发度 | 全局一把锁 | 全局一把锁 | 分段锁/CAS |

### 14.7 面试回答模板

**问：HashMap 的底层数据结构是什么？**

> HashMap 在 Java 7 使用数组+链表，Java 8 增加了红黑树。当链表长度超过8时会转换为红黑树，这样可以把最坏情况 O(n) 的查找优化到 O(log n)。
>
> 底层是一个 Node 数组（table），每个数组位置可以放一个 Node。Node 是单向链表节点，包含 hash、key、value、next。当多个 key 映射到同一个数组位置时，它们以链表形式存储。

**问：HashMap 的 put 流程是什么？**

> put 操作分三步：第一步调用 hash() 方法计算 key 的 hash 值，用高低16位异或让 hash 更散列；第二步通过 `(n-1) & hash` 计算数组下标，定位到具体的桶；第三步遍历该桶的链表/红黑树，如果找到相同 key 就更新值，如果没找到就在链表头部插入新节点。最后检查是否需要扩容（size 超过 threshold）。
>
> Java 8 的特殊之处是链表用尾插法插入，而 Java 7 是头插法，所以 Java 8 避免了并发扩容时的环形链表问题。

### 15.2 synchronized 的底层原理

#### 对象头结构（Mark Word）

```
64位 JVM 对象头（Mark Word）：
┌────────────────────────────────────────────────────────┐
│ 25 bit        │ 31 bit    │ 1 bit   │ 4 bit   │ 1 bit │
│  unused       │ hashCode  │   GC age│偏向模式 │ 锁类型│
│  hashCode     │ 分代年龄  │         │         │       │
└────────────────────────────────────────────────────────┘
                        Mark Word 结构（无锁状态）

锁升级后的 Mark Word：
┌────────────────────────────────────────────────────────┐
│ 54bit                      │ 2 bit   │ 4 bit   │ 1 bit │
│  指向栈帧的指针（轻量锁）/  无锁标记 │  偏向模式│  锁类型│
│  指向互斥量指针（重量锁）   │         │         │       │
└────────────────────────────────────────────────────────┘
```

#### monitorenter / monitorexit 字节码指令

```java
// Java 源代码
public synchronized void method() {
    // do something
}

// 编译后的字节码
 0: aload_0
 1: monitorenter           // 进入 monitor（获取锁）
 2: ...                   // 方法体
 3: monitorexit           // 退出 monitor（释放锁）
 4: return
```

**monitorenter 原理**：
- 每个 Java 对象都关联一个 monitor（管程）
- 线程执行 `monitorenter` 时，尝试获取对象的 monitor 所有权
- 如果 monitor 被占用，线程进入阻塞等待

### 15.3 锁升级机制（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）

```
┌────────┐    偏向锁        ┌────────┐    轻量级锁       ┌────────────┐   重量级锁
│  无锁   │ ─────────────▶ │ 偏向锁 │ ──────────────▶ │  轻量级锁  │ ──────────▶│  重量级锁  │
│  00    │ 第一个线程访问  │  01    │  锁竞争发生      │    00      │  锁竞争激烈 │    10    │
└────────┘                └────────┘  多线程交替       └────────────┘            └────────────┘
     │                        │              │              │                      │
     │                        │              │              │                      │
     ▼                        ▼              ▼              ▼                      ▼
 无锁状态          线程ID记录在        CAS 修改          栈帧中建立         OSMutex
 可重入/不可重入    Mark Word           Mark Word          锁记录              阻塞等待
```

#### 第一阶段：偏向锁（Biased Locking）

**场景**：只有一个线程访问同步块

**原理**：
- 第一次获取锁时，在 Mark Word 中记录线程ID
- 之后该线程进入同步块，只需检查 Mark Word 中的线程ID
- 无需任何原子操作，真正实现"偏向"

```java
// 偏向锁获取过程
if (mark.is-biased() && mark.biased-locker == current-thread) {
    // 偏向锁，且是当前线程 → 直接进入同步块（零开销）
    lock();
} else {
    // 尝试 CAS 修改 Mark Word 获取偏向锁
    if (mark.CAS-set-biased(current-thread)) {
        // 成功 → 偏向锁
        lock();
    } else {
        // 失败 → 撤销偏向锁，升级为轻量级锁
        inflate-and-acquire(mark);
    }
}
```

**撤销偏向锁的条件**：
- 其他线程尝试获取该锁
- 调用了 `Object.hashCode()`
- 调用了 `Object.wait()/notify()`

#### 第二阶段：轻量级锁（Lightweight Locking）

**场景**：多个线程交替访问同步块，无长时间竞争

**原理**：
- 在线程栈帧中创建锁记录（Lock Record）
- 将 Mark Word 复制到锁记录
- 用 CAS 将 Mark Word 修改为指向锁记录的指针

```java
// 轻量级锁获取过程
// 1. 在线程栈帧中创建锁记录
LockRecord lock-record = new LockRecord();

// 2. 复制 Mark Word 到锁记录
lock-record.set-displaced-header(mark-word);

// 3. CAS 修改 Mark Word 指向锁记录
if (mark.CAS-set(lock-record, current-thread)) {
    // 成功 → 获得轻量级锁
    lock();
} else {
    // 失败 → 存在锁竞争，升级为重量级锁
    inflate-and-acquire-heavy-lock(mark);
}
```

**轻量级锁的解锁**：
```java
// 用 CAS 将 Mark Word 还原
if (mark.CAS-set(original-mark-word, current-thread)) {
    // 成功 → 解锁成功
} else {
    // 失败 → 说明有其他线程在等待，唤醒等待线程（重量级锁逻辑）
    slow-exit(mark);
}
```

#### 第三阶段：重量级锁（Heavyweight Locking）

**场景**：多线程同时竞争同一把锁

**原理**：
- 不再使用 CAS，而是切换到内核态
- 通过 OSMutex 实现，线程被挂起
- 抢锁失败的线程进入等待队列

```
用户态 ──▶ 内核态切换（系统调用）
  │
  │ 线程A获取锁
  ▼ 成功，进入临界区
  │
  │ 线程B获取锁
  ▼ 失败，阻塞
  ├──▶ OS 将线程B挂起（等待调度）
  ├──▶ 线程A释放锁
  ├──▶ OS 唤醒线程B
  └──▶ 线程B 进入临界区
```

**性能问题**：用户态到内核态的切换成本高，约 1000-10000 个 CPU 时钟周期

### 15.4 锁升级的不可逆性

```
偏向锁 ──▶ 轻量级锁 ──▶ 重量级锁（单向不可逆）
  │            │
  │            └── 可以直接到重量级锁（跳过偏向锁）
  │
  └── 可以直接到重量级锁（跳过偏向锁和轻量级锁）
```

**为什么不可逆？**
- 锁一旦升级为重量级锁，就无法降级回去
- 因为重量级锁使用了 OSMutex，状态记录在 Mark Word 中
- 降级需要额外的状态管理，反而增加复杂度

### 15.5 synchronized vs ReentrantLock 对比

| 维度 | synchronized | ReentrantLock |
|------|--------------|---------------|
| 特性 | 可重入、非公平 | 可重入、可公平/非公平 |
| 等待方式 | 阻塞等待 | 可中断/超时等待 |
| 锁释放 | 自动释放 | 手动释放（必须 finally） |
| Condition | 不支持 | 支持多个 Condition |
| 底层 | monitor (内核态) | AQS + CAS (用户态) |
| 性能（低竞争） | 偏向锁优化后很快 | 差不多 |
| 性能（高竞争） | 重量级锁慢 | 可用读写锁优化 |

### 15.6 面试回答模板

**问：synchronized 的底层原理是什么？**

> synchronized 的底层依赖 Monitor（管程）实现。每个 Java 对象都关联一个 Monitor，当执行 `monitorenter` 指令时，线程尝试获取 Monitor 的所有权，如果被占用则阻塞。`monitorexit` 指令释放锁。
>
> 在 Java 6 之后，synchronized 引入了锁升级机制：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。第一个线程访问时用偏向锁，线程ID记录在对象头中，之后进入只需要检查ID无需原子操作；多个线程交替访问时升级为轻量级锁，用 CAS 在栈帧中创建锁记录；真正有竞争时升级为重量级锁，使用 OSMutex 挂起线程。

**问：锁升级过程是怎样的？为什么不能降级？**

> 锁升级是单向不可逆的：偏向锁 → 轻量级锁 → 重量级锁。
>
> 偏向锁针对单个线程，如果另一个线程来竞争，撤销偏向锁，升级为轻量级锁。轻量级锁通过 CAS 修改 Mark Word，如果 CAS 失败说明有竞争，升级为重量级锁。重量级锁使用 OSMutex，线程被挂起等待。
>
> 不能降级是因为：锁状态记录在 Mark Word 中，升级后原来的状态信息已经丢失，无法还原。如果要降级需要额外维护状态，反而增加复杂度。

## 十六、MySQL MVCC 机制详解

### 16.1 为什么需要 MVCC

**事务并发的问题**：

| 问题 | 定义 | 例子 |
|------|------|------|
| 脏读 | 读取了其他事务未提交的数据 | 事务A修改了数据但未提交，事务B读取了这些数据 |
| 不可重复读 | 同一事务中两次读取数据不一致 | 事务A读取数据，事务B修改并提交，事务A再次读取 |
| 幻读 | 同一事务中两次查询结果数量不一致 | 事务A查询满足条件的数据，事务B插入新数据并提交，事务A再次查询 |

**MVCC 的作用**：在不锁表的情况下，解决脏读、不可重复读、幻读问题

### 16.2 MVCC 的核心概念

#### 隐藏列

InnoDB 中，每行数据有两个隐藏列：

```sql
-- 实际的表结构比看起来多了两列
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    age INT
    -- 以下是隐藏列（不可见）
    -- db_trx_id    创建版本号（事务ID）
    -- db_roll_ptr  删除版本号（事务ID）
);
```

| 隐藏列 | 说明 |
|--------|------|
| `db_trx_id` | 创建这条记录的事务ID |
| `db_roll_ptr` | 回滚指针，指向 undo log 链表的指针 |
| `delete_flag` | 删除标记（InnoDB 把删除当成更新，设置删除标记） |

####Undo Log 链表演示

```
事务A（ID=100）插入一条记录：

undo log 链表：
┌─────────────┐
│  Record v1  │ ← 指向这条记录的指针
│  db_trx_id=100
│  db_roll_ptr=null
│  name="张三"
└─────────────┘

事务B（ID=101）修改这条记录：

undo log 链表：
┌─────────────┐    ┌─────────────┐
│  Record v2  │───▶│  Record v1  │
│  db_trx_id=101    │  db_trx_id=100
│  db_roll_ptr=     │  db_roll_ptr=null
│    指向v1的指针   │  name="张三"
│  name="李四"      │  (历史版本)
└─────────────┘    └─────────────┘

事务B看到的是：name="李四"（最新版本）
事务A看到的是：name="张三"（通过undo链找到的历史版本）
```

### 16.3 ReadView（读视图）

**ReadView 是 MVCC 的关键**，它定义了"在某个时间点，能看到哪些数据"。

```java
class ReadView {
    long creator_trx_id;        // 当前事务的ID
    List<Long> active_trx_ids;  // 活跃事务ID列表（未提交的事务）
    long low_limit_id;          // 最小活跃事务ID
    long up_limit_id;           // 最大事务ID + 1
    boolean m_changes_are_visible; // 当前事务的改动是否可见
}
```

**可见性判断规则**：

```java
// 判断某条记录对当前事务是否可见
public boolean is_visible(long record_trx_id) {
    // 规则1：记录的事务ID小于最小活跃事务ID → 可见（事务已提交）
    if (record_trx_id < low_limit_id) {
        return true;
    }

    // 规则2：记录的事务ID是当前事务自己创建的 → 可见（自己的改动）
    if (record_trx_id == creator_trx_id) {
        return true;
    }

    // 规则3：记录的事务ID在活跃列表中 → 不可见（其他事务未提交）
    if (active_trx_ids.contains(record_trx_id)) {
        return false;
    }

    // 规则4：其他情况 → 可见（已提交的事务）
    return true;
}
```

### 16.4 不同隔离级别下的 ReadView 策略

#### READ COMMITTED（每次读取都生成新 ReadView）

```
时间线：
T1: 事务A开启，ReadView = [A]
T2: 事务B开启，ReadView = [A, B]
T3: 事务C开启，ReadView = [A, B, C]
T4: 事务B提交 ← ReadView 重生成！
T5: 事务A查询 → ReadView = [A, C]（B已提交，不在列表中）
```

**特点**：
- 每次读取都生成新的 ReadView
- 事务B提交后，事务A可以看到B的改动
- 可能出现不可重复读：事务A两次读取，中间B提交了

#### REPEATABLE READ（事务开始时生成 ReadView，整个事务复用同一个）

```
时间线：
T1: 事务A开启，ReadView = [A]
T2: 事务B开启
T3: 事务B提交
T4: 事务A查询 → ReadView = [A]（复用，忽略B的提交）
T5: 事务A再次查询 → ReadView = [A]（复用，结果相同）
```

**特点**：
- 事务开始时生成 ReadView，整个事务复用
- 同一事务内多次读取结果一致
- MySQL 的默认隔离级别
- 通过间隙锁防止幻读

### 16.5 MVCC 读取流程

```java
// MVCC 读取数据的伪代码
public Row select(long transaction_id) {
    while (true) {
        // 1. 从最新版本开始
        Row current = get_latest_row(trx_id);

        // 2. 判断该版本是否可见
        if (is_visible(current, transaction_id)) {
            // 3. 如果被标记为删除，检查删除事务是否可见
            if (current.delete_flag && current.delete_trx_id == transaction_id) {
                return null;  // 已删除，看不到
            }
            return current;  // 可见，返回
        }

        // 4. 不可见，通过回滚指针找上一个版本
        Row prev = get_prev_version(current);

        // 5. 如果没有更早的版本，返回空
        if (prev == null) {
            return null;
        }
    }
}
```

### 16.6 快照读 vs 当前读

#### 快照读（Snapshot Read）

```sql
-- 普通 SELECT 语句，使用 MVCC 读取历史版本
SELECT * FROM user WHERE id = 1;
-- 返回的是事务开始时的快照数据
```

#### 当前读（Current Read）

```sql
-- 加锁读取，读取最新数据
SELECT * FROM user WHERE id = 1 FOR UPDATE;  -- 排他锁
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁

-- 修改操作，自动加锁
INSERT INTO user VALUES(...);  -- 排他锁
UPDATE user SET ... WHERE ...;  -- 排他锁
DELETE FROM user WHERE ...;  -- 排他锁
```

### 16.7 MVCC + 间隙锁 解决幻读

在 REPEATABLE READ 级别下：

```sql
-- 事务A
BEGIN;
SELECT * FROM user WHERE age > 20;  -- 返回2条记录

-- 事务B（在事务A之前执行）
BEGIN;
INSERT INTO user VALUES(3, '王五', 25);  -- 插入一条 age=25 的记录
COMMIT;

-- 事务A
SELECT * FROM user WHERE age > 20;  -- 快照读，还是返回2条
UPDATE user SET name = '赵六' WHERE age > 20;  -- 当前读，对age>20的记录加锁
-- 此时会锁住 age>20 的范围（包括事务B插入的新记录的间隙）
COMMIT;
```

**间隙锁的范围**：假设 age 索引有值 15, 20, 30，`age > 20` 会锁住 (20, +∞) 的间隙，包括 (20, 30) 和 (30, +∞)。

### 16.8 面试回答模板

**问：MySQL 的 MVCC 是什么？是怎么工作的？**

> MVCC（多版本并发控制）是 MySQL InnoDB 引擎实现事务隔离级别的一种方式，核心是通过版本链和 ReadView 实现不加锁的读。
>
> InnoDB 每行数据有两个隐藏列：创建事务ID和回滚指针。回滚指针指向 undo log 链表，形成版本链。读取数据时，通过 ReadView 判断版本是否可见：事务ID小于最小活跃ID说明已提交，如果等于自己则是自己的改动，如果在活跃列表中说明未提交不可见。
>
> 不同隔离级别下 ReadView 生成策略不同。READ COMMITTED 每次读取都生成新 ReadView，所以可能看到其他事务提交的改动。REPEATABLE READ 在事务开始时生成 ReadView，整个事务复用，所以同一事务内多次读取结果一致。

**问：MVCC 能完全解决幻读吗？**

> MVCC 的快照读可以解决快照幻读，但当前读不能。快照读（普通 SELECT）通过 MVCC 读取历史版本，不会看到其他事务插入的新记录。但当前读（SELECT FOR UPDATE / UPDATE / DELETE / INSERT）会加锁，锁住索引范围。REPEATABLE READ 级别下使用间隙锁，锁住插入新记录的间隙，防止幻读。

**问：MVCC 和锁的区别是什么？**

> MVCC 是乐观并发控制，适合读多写少的场景，读操作不加锁，通过版本号判断可见性，性能高但可能需要回滚。锁是悲观并发控制，写操作加锁，锁住资源后其他事务无法访问，保证强一致性但性能低。MVCC 和锁可以结合使用：用 MVCC 处理读，用锁处理写。

## 十七、MySQL 事务与锁的底层原理

### 17.1 InnoDB 锁的分类

```
┌──────────────────────────────────────────────────────────────┐
│                         InnoDB 锁体系                          │
├────────────────────────┬─────────────────────────────────────┤
│  共享锁（S锁）          │  读锁，多个事务可以同时持有            │
│  排他锁（X锁）          │  写锁，独占，其他事务不能获取任何锁    │
├────────────────────────┼─────────────────────────────────────┤
│  行锁                  │  锁住一行数据                         │
│  表锁                  │  锁住整张表（使用表锁时）              │
│  意向锁                │  表锁和行锁之间的桥梁（IX / IS）        │
│  Gap Lock              │  锁住记录之间的间隙                    │
│  Next-Key Lock         │  行锁 + Gap Lock，锁住前闭后开区间    │
│  插入意向锁            │  插入操作特有的锁                      │
└────────────────────────┴─────────────────────────────────────┘
```

#### 行锁的类型

| 锁类型 | 生效条件 | 能共存吗 | 典型 SQL |
|--------|---------|---------|----------|
| 共享锁（S） | `SELECT ... LOCK IN SHARE MODE` | S锁之间可共存 | 查询时加共享锁 |
| 排他锁（X） | `UPDATE / DELETE / SELECT FOR UPDATE` | 互斥 | 写操作时加排他锁 |
| 记录锁（Record Lock） | 精确匹配索引查找（如 `WHERE id = 5`） | 不同记录可共存 | `WHERE id = 1` |
| 间隙锁（Gap Lock） | 范围查询且索引存在（如 `WHERE id > 5`） | 同间隙不冲突 | `WHERE id > 5` |
| Next-Key Lock | 范围查询（InnoDB 默认在 RR 级别使用） | 锁前闭后开区间 | `WHERE id > 5` |

#### 意向锁（表锁和行锁的桥梁）

```
// 为什么需要意向锁？
// 因为加行锁之前需要先加表级意向锁，通知其他事务"我即将在某些行加锁"

事务A: UPDATE user SET age = 20 WHERE id = 1;
  → 意向排他锁（IX）→ 表级意向锁
  → 排他锁（X）→ 行级锁

事务B: LOCK TABLE user WRITE;  -- 尝试加表锁
  → 检查表级意向锁
  → 发现有 IX → 阻塞等待（而不是逐行检查）
  → 省去了逐行扫描是否有锁的开销
```

### 17.2 MVCC 如何配合锁实现事务隔离

```
┌─────────────────────────────────────────────────────────────────┐
│                    MVCC + 锁 的协作机制                           │
├────────────────────┬──────────────────┬─────────────────────────┤
│  操作类型           │  使用机制         │  说明                    │
├────────────────────┼──────────────────┼─────────────────────────┤
│  SELECT            │  MVCC（快照读）   │  不加锁，读历史版本        │
│  SELECT ... FOR UPDATE |  当前读 + X锁   │  加排他锁，读取最新数据   │
│  INSERT            │  X锁 + Gap锁     │  锁住插入位置             │
│  UPDATE            │  X锁 + Gap锁     │  锁住更新前和更新后       │
│  DELETE            │  X锁 + Gap锁     │  锁住删除位置             │
└────────────────────┴──────────────────┴─────────────────────────┘
```

### 17.3 锁是如何产生的

#### 17.3.1 锁的来源：SQL 执行计划决定

```sql
-- 锁的产生取决于SQL使用的索引类型，而不是SQL本身

-- 场景1：使用主键索引精确查找 → 记录锁
SELECT * FROM user WHERE id = 5 FOR UPDATE;
-- 锁：id=5 的行（记录锁）

-- 场景2：使用二级索引范围查找 → Next-Key Lock
SELECT * FROM user WHERE age > 20 FOR UPDATE;
-- 锁：(20, +∞) 的前闭后开区间（Next-Key Lock）
-- 如果 age 索引有值 20, 25, 30
-- 锁范围：(20, 25] + [25, 30) + (30, +∞)

-- 场景3：无索引查找 → 全表扫描 → 表锁
SELECT * FROM user WHERE name LIKE '%张%' FOR UPDATE;
-- 锁：整张表（因为没有索引可走）
```

#### 17.3.2 锁的加锁过程

```sql
BEGIN;

UPDATE user SET age = 30 WHERE id > 10;
-- InnoDB 执行流程：
-- 1. 通过 id 索引找到 id > 10 的第一条记录
-- 2. 对这条记录加 X 锁（排他锁）
-- 3. 检查下一条记录是否在范围内
-- 4. 如果在，继续加锁；如果不在，停止
-- 5. 对最后一条在范围内的记录，加 Gap Lock 防止新插入
```

#### 17.3.3 一条 UPDATE 语句的锁生命周期

```
UPDATE user SET age = 30 WHERE id > 10;
         │
         ▼
┌─────────────────────────────────────────────────┐
│  Step 1: 找到 id=11 的记录                       │
│  对记录加 X 锁（行锁）                           │
└─────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────┐
│  Step 2: 找到 id=12, 13, 14...                   │
│  逐一对每条记录加 X 锁                          │
└─────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────┐
│  Step 3: 找到 id > 10 的最后一条（比如 100）      │
│  对最后一条加 X 锁                              │
│  同时在 (100, +∞) 加 Gap Lock                   │
│  防止新插入 id > 10 的记录                       │
└─────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────┐
│  Step 4: 事务提交 / 回滚                         │
│  所有锁释放                                     │
└─────────────────────────────────────────────────┘
```

### 17.4 事务提交时锁的释放时机

```
事务A:
  BEGIN;
  UPDATE user SET age = 30 WHERE id > 10;  -- 加锁
       │
       ▼
  SELECT * FROM user WHERE id > 10;       -- 读（快照读，无锁）
       │
       ▼
  UPDATE user SET name = 'test' WHERE id = 5;  -- 再次加锁
       │
       ▼
  COMMIT;  -- 所有锁一次性释放

在 COMMIT 之前，所有加过的锁都持有。
这叫 "两阶段锁协议"（2PL）：
  - 加锁阶段：只加锁，不释放锁
  - 解锁阶段：释放所有锁
```

### 17.5 死锁的产生与检测

#### 死锁产生的经典场景

```
事务A:
BEGIN;
UPDATE user SET age = 20 WHERE id = 1;  -- 锁住 id=1
         │
         ▼
UPDATE user SET age = 20 WHERE id = 2;  -- 等待 id=2 的锁（事务B持有）

事务B:
BEGIN;
UPDATE user SET age = 20 WHERE id = 2;  -- 锁住 id=2
         │
         ▼
UPDATE user SET age = 20 WHERE id = 1;  -- 等待 id=1 的锁（事务A持有）
         │
         ▼
死锁！两个事务相互等待对方持有的锁
```

#### InnoDB 的死锁检测机制

```
InnoDB 有一个"等待图"（Wait-For Graph）检测死锁：

每一条边：事务T1 等待 事务T2 持有的锁
          事务T2 等待 事务T3 持有的锁
          ...
          事务Tn 等待 事务T1 持有的锁
          → 闭环 = 死锁！

检测到死锁后：
  InnoDB会选择"回滚代价最小的事务"进行回滚
  代价计算：undo log 记录数量最少的事务

可以通过以下命令查看死锁日志：
SHOW ENGINE INNODB STATUS;
```

#### 避免死锁的方法

| 方法 | 说明 |
|------|------|
| **固定顺序访问资源** | 所有事务按相同顺序 UPDATE（先更新 id=1 再更新 id=2） |
| **减少锁范围** | 只锁定必要的行，不要用无索引的 UPDATE |
| **降低事务时长** | 减少在持有锁期间的 RPC / 远程调用 |
| **合理设置隔离级别** | 读多写少场景可用 RC 级别，减少锁 |
| **使用表锁** | `LOCK TABLE ... WRITE` 串行化，但性能差 |

### 17.6 面试回答模板

**问：MySQL 的锁是怎么产生的？什么SQL会加锁？**

> MySQL InnoDB 的锁是根据 SQL 的执行计划动态加的，不是 SQL 本身决定的。精确索引查找加记录锁，只锁一行；范围索引查找在 RR 级别下加 Next-Key Lock，锁住前闭后开区间；无索引查找走全表扫描，会锁住整张表。
>
> 拿 UPDATE 来说：`WHERE id = 5` 加记录锁，`WHERE id > 5` 加 Next-Key Lock（[5, +∞)），如果是唯一索引且精确查找则只加记录锁。INSERT 加排他锁和插入意图锁，DELETE 加排他锁和 Gap Lock。

**问：事务提交时锁是什么时候释放的？**

> 遵循两阶段锁协议（2PL）。加锁阶段只加锁不释放锁，解锁阶段在事务提交或回滚时一次性释放所有锁。这意味着在整个事务执行期间，所有加过的锁都持有。所以事务要尽量短，持有锁期间不要做 RPC 调用或等待用户输入。

**问：死锁是怎么产生的？怎么避免？**

> 死锁产生的原因是多个事务以不同的顺序访问资源，导致相互等待。经典场景是事务A先锁id=1再锁id=2，事务B先锁id=2再锁id=1，形成循环等待。InnoDB 通过等待图检测死锁，发现后会回滚 undo log 记录最少的事务。避免死锁的方法是**按固定顺序访问资源**，所有事务都以相同顺序加锁。

## 十八、ThreadLocal 能在微服务之间传递吗？

### 18.1 直接回答：不能

**ThreadLocal 是线程绑定的**，ThreadLocal 的数据存储在 Thread 的 ThreadLocalMap 中，**只在同一个线程内有效**。

```
微服务调用链路：
服务A → 服务B → 服务C
  │         │         │
  ThreadA   ThreadB   ThreadC  ← 每个服务是不同的线程
  │         │         │
  ThreadLocalA  ThreadLocalB  ThreadLocalC  ← 各自独立，互不可见
```

### 18.2 为什么 ThreadLocal 不能跨线程

```java

    ThreadLocal.ThreadLocalMap threadLocals = null;

    Entry[] table;
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;  // 存储的值
        Entry(ThreadLocal<?> k, Object v) {
            super(k);
            value = v;
        }
    }
}
```

**ThreadLocal 的 get() 方法**：

```java

    // 获取当前线程的 ThreadLocalMap

    // 从当前线程的 map 中找
```

## 十九、CompletableFuture 线程协作原理与线程通信机制

### 19.1 CompletableFuture 执行结果如何通知主线程

#### 19.1.1 核心原理：Future 模式 + CAS + AQS

`CompletableFuture` 内部有一个 `result` 字段用于存储执行结果，和一个 `stack` 字段用于存储等待的回调链表。

```java
// CompletableFuture 的核心字段
public class CompletableFuture<T> {
    // 结果：null=进行中，result=已完成（正常值），EXCEPTION=失败
    volatile Object result;

    // 栈：存储等待的回调（Completion链表）
    volatile Completion stack;

    // CAS 设置结果
    final boolean casResult(Object expected, Object newResult) {
        U.compareAndSwapObject(this, RESULT, expected, newResult);
    }
}
```

#### 19.1.2 完整流程解析

```java
// CompletableFuture.supplyAsync() 的内部实现
public static <T> CompletableFuture<T> supplyAsync(Supplier<T> supplier, Executor executor) {
    // 1. 创建 CompletableFuture（初始状态 result=null）
    CompletableFuture<T> future = new CompletableFuture<>();

    // 2. 提交任务到线程池
    executor.execute(() -> {
        T value;
        try {
            value = supplier.get();  // 子线程执行业务逻辑
        } catch (Throwable ex) {
            // 3. 失败：标记异常结果
            future.completeExceptionally(ex);
            return;
        }
        // 4. 成功：用 CAS 原子操作设置结果（关键！）
        future.complete(value);
    });

    return future;  // 主线程拿到 future，result 此时可能还是 null
}

// future.complete() 的实现
public boolean complete(T value) {
    if (result == null) {
        if (RESULT.compareAndSet(this, null, value)) {
            // 5. CAS 成功，触发所有等待的回调
            postComplete();  // ← 通知主线程的关键
            return true;
        }
    }
    return false;
}

// postComplete：触发所有等待的回调
private void postComplete() {
    Completion c;
    while ((c = stack) != null) {
        if (STACK.compareAndSet(this, c, null)) {
            c.run();  // 执行回调（thenApply / thenAccept / join 等）
        }
    }
}
```

#### 19.1.3 主线程等待的几种方式

```java
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    Thread.sleep(2000);
    return "result";
}, executor);

// 方式一：get() — 阻塞等待，带超时
try {
    String result = future.get();              // 无限阻塞
    String result = future.get(3, TimeUnit.SECONDS);  // 3秒超时
} catch (InterruptedException | ExecutionException e) {}

// get() 的内部：result == null → 阻塞等待；result != null → 返回；EXCEPTION → 抛 ExecutionException

// 方式二：join() — 同 get() 但抛 RuntimeException，无需 try-catch
String result = future.join();

// 方式三：whenComplete / handle — 回调，不阻塞主线程
future.whenComplete((result, ex) -> {
    if (ex != null) {
        System.out.println("失败: " + ex.getMessage());
    } else {
        System.out.println("成功: " + result);
    }
});
// 主线程继续执行自己的代码，不用等待，子线程完成后自动回调

// 方式四：allOf / anyOf — 等待多个完成
CompletableFuture.allOf(f1, f2, f3).join();  // 等待所有完成
CompletableFuture.anyOf(f1, f2, f3).join(); // 等待任意一个完成
```

### 19.2 线程通信：wait / notify 机制

#### 19.2.1 为什么需要 wait / notify

```
线程A（持有锁）：条件不满足 → wait() 阻塞，释放锁
线程B（持有锁）：修改了条件 → notify() 唤醒一个等待的线程
线程A（被唤醒）：从 wait() 返回，重新获取锁，继续执行
```

**核心点**：wait / notify 必须在 `synchronized` 代码块中使用，因为：
- wait 会释放锁（这是唯一的释放锁方式）
- notify 通知需要从 synchronized 块内部调用
- 防止竞态条件：检查条件 → wait 之间被其他线程修改

#### 19.2.2 wait / notify 原理图

```
synchronized (obj) {
    while (条件不满足) {        ← 循环检查（防止伪唤醒）
        obj.wait();             ← 线程A 阻塞，释放锁
    }
    // 条件满足，执行逻辑
}

synchronized (obj) {              ← 线程B 获得锁
    满足条件了
    obj.notify();                 ← 唤醒一个等待的线程
}                                ← 线程B 释放锁

线程A 从 wait() 返回
        │
        ▼
重新竞争锁（可能失败，要等B释放）
        │
        ▼
获取到锁 → while (条件不满足) → obj.wait()  ← 再次检查（防止伪唤醒）
        │
        ▼
执行逻辑
```

#### 19.2.3 wait / notify 底层实现（HotSpot JVM）

```c
// JVM 源码简化版：ObjectMonitor::wait()
void ObjectMonitor::wait() {
    // 1. 将当前线程加入等待队列（EntryList）
    // 2. 调用 park() 挂起线程（底层用 pthread_cond_wait）
    // 3. 线程被唤醒后，重新进入 EntryList，等待获取锁
    // 注意：wait 会释放 monitor（锁）
}

// ObjectMonitor::notify()
void ObjectMonitor::notify() {
    // 1. 从 EntryList 中取出一个线程
    // 2. 移动到 ContentionList（竞争队列）
    // 3. 唤醒该线程（底层用 pthread_cond_signal）
    // 注意：notify 只是移动线程位置，不释放锁
}
```

#### 19.2.4 经典生产者-消费者实现

```java
public class ProducerConsumer {
    private static final int CAPACITY = 10;
    private final Queue<Integer> queue = new LinkedList<>();
    private final Object lock = new Object();

    public void produce(int value) throws InterruptedException {
        synchronized (lock) {
            while (queue.size() == CAPACITY) {
                lock.wait();  // 队列满，等待
            }
            queue.add(value);
            lock.notify();    // 唤醒消费者
        }
    }

    public void consume() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty()) {
                lock.wait();  // 队列空，等待
            }
            int value = queue.poll();
            lock.notify();    // 唤醒生产者
        }
    }
}
```

#### 19.2.5 wait / notify vs LockSupport.park / unpark

| 维度 | wait/notify | LockSupport.park/unpark |
|------|------------|-------------------------|
| 需要 synchronized | 必须 | 不需要 |
| 可以指定线程 | 不能（随机唤醒） | 可以指定唤醒哪个线程 |
| 能否被中断 | 可以（抛 InterruptedException） | 可以 |
| 底层 | Monitor + pthread_cond_wait | park() 系统调用 |
| 令牌/许可 | 无 | 有（permit） |
| 适用场景 | 简单协作 | 线程池/并发框架 |

```java
// LockSupport 示例：线程池核心原理
public Runnable take() {
    while (task == null) {
        LockSupport.park();  // 阻塞，没有 synchronized 要求
    }
    Runnable r = task;
    task = null;
    return r;
}

public void submit(Runnable task) {
    workQueue.add(task);
    LockSupport.unpark(workerThread);  // 唤醒指定线程
}
```

### 19.3 sleep / yield / join 的底层原理

#### 19.3.1 sleep（休眠不释放锁）

```java
synchronized (lock) {
    Thread.sleep(3000);  // 持锁休眠3秒，其他线程无法进入这段 synchronized
}
// 3秒后自动唤醒，继续执行

// sleep 的底层：
// Thread.sleep(ms) → JVM → pthread_cond_timedwait / sleep系统调用
// → 线程休眠，时间片不分配，但不释放锁
// → 时间到自动唤醒，回到 RUNNABLE
```

#### 19.3.2 yield（让步，主动让出CPU）

```java
Thread.yield();
// 线程从 RUNNABLE 变为 RUNNABLE（就绪）
// 表示"我愿意让出CPU，让其他线程先执行"
// 但调度器可以忽略这个提示
```

#### 19.3.3 join（等待其他线程完成）

```java
Thread thread = new Thread(() -> {
    Thread.sleep(2000);
});
thread.start();
thread.join();  // 主线程阻塞，等待 thread 执行完毕
System.out.println("主线程继续");
```

**join 的底层原理**：

```java
// Thread.join() 的实现（简化）
public final void join() throws InterruptedException {
    synchronized (lock) {
        while (isAlive()) {  // 检查子线程是否还在运行
            lock.wait();     // 释放锁并等待
        }
    }
}

// 主线程调 join 后：
// 1. 主线程获取 thread 对象锁
// 2. while(isAlive()) 检查子线程是否完成
// 3. 子线程未完成 → 主线程 wait()，释放锁
// 4. 子线程执行完毕 → 调用 notifyAll() 通知
// 5. 主线程被唤醒，再次检查 isAlive() → false → 跳出循环
```

**join 的完整时序**：

```
子线程 start()
         │
         ▼
主线程 thread.join()
         │
         ▼
主线程获取 thread 对象锁
         │
         ▼
while (isAlive()) → true → 主线程 wait()，释放锁
         │
         │            子线程 run() 执行
         │            子线程执行完毕
         │            子线程 notifyAll()（JVM内部调用）
         │◀──────────┘
         │
主线程重新获取锁（wait 返回后自动获取）
         │
         ▼
while (isAlive()) → false，跳出循环
         │
         ▼
主线程继续执行
```

```
                                           │     wait(timeout)
                                           ▼
                              ┌──────────────────────────────────────┐
                              │         WAITING（无期限等待）           │
                              │   wait() / LockSupport.park()         │
                              │   join() / condition.await()           │
                              └──────┬───────────────────────────────┘
                                     │   notify() / unpark() /
                                     │   notifyAll() / LockSupport.unpark()
                                     └──────────────────────────────────┘
                                           │
                                           ▼
                              ┌──────────────────────────────────────┐
                              │         BLOCKED（阻塞等锁）           │
                              │   进入 synchronized 等待获取锁        │
                              │   或 Lock.lock() 失败                 │
                              └──────┬───────────────────────────────┘
                                     │   获取到锁
                                     ▼
                              ┌──────────────────────────────────────┐
                              │   RUNNABLE（继续执行）                 │
                              └──────────────────────────────────────┘
```

### 19.5 面试回答模板

**问：CompletableFuture 子线程执行完了，怎么通知主线程的？**

> CompletableFuture 内部用 CAS 设置一个 result 字段。子线程执行 `complete(value)` 时，用 Unsafe CAS 把结果原子写入 result，设置成功后会触发 `postComplete()`，遍历栈中的所有回调（thenApply、whenComplete 等）并执行。主线程调用 `get()/join()` 时，如果 result 还是 null，就阻塞等待——等待的实现基于 AQS，当 result 被设置时，get 的线程会被唤醒并返回结果。

**问：sleep 和 wait 的区别是什么？**

> 核心区别是**是否释放锁**。sleep 是 Thread 类的方法，调用后线程进入 TIMED_WAITING 状态，但**不释放已持有的锁**，适合定时任务。wait 是 Object 类的方法，必须在 synchronized 中调用，调用后线程进入 WAITING 状态，**会释放锁**，适合线程间协作。另外 wait 可以用 notify/notifyAll 唤醒，也可以超时自动唤醒；sleep 只能等时间到了自动醒。

**问：join 是怎么实现的？**

> join 底层是 wait + notifyAll 的组合。主线程调用 `thread.join()` 时，先获取 thread 对象的内置锁，然后 while 检查 thread 是否还活着（isAlive），如果活着就调用 wait() 释放锁并等待。子线程执行完毕后，在 exit 流程中会调用 notifyAll() 通知所有等待的线程，主线程被唤醒后再次检查 isAlive 为 false，跳出循环继续执行。

**问：为什么 wait 要用 while 而不是 if？**

> 因为存在**伪唤醒**（spurious wakeup）——wait 可能被意外唤醒而不调用 notify。标准要求 wait 必须在循环中调用，每次被唤醒都要重新检查条件。如果用 if，伪唤醒后会直接跳过检查继续执行，导致逻辑错误。正确模式是 `while (!condition) { lock.wait(); }`。

**问：notify 和 notifyAll 怎么选？**

> 只唤醒一个线程用 notify，但需要确保**所有等待的线程做的是同一件事**且**只有一个能成功**。如果多个线程等待不同条件，或者多个线程竞争同一资源但只有一个能成功，就需要用 notifyAll 全部唤醒，让它们重新检查条件。比如生产者-消费者中，生产者 notify 消费者（因为等的是"有数据"这同一件事），消费者 notify 生产者（等的是"有空间"），这样不会唤醒无关的线程。

## 二十、缓存与数据库一致性：延时双删与 Binlog 订阅

### 20.1 为什么缓存一致性是难题

```
问题根源：缓存（Redis）和数据库（MySQL）是两个独立的存储
         操作不是原子的，时间差内可能数据不一致

写操作时序问题：
T1: 更新数据库 → data = "new_value"
T2: 删除缓存 → delete(key)
      ↑
      但如果在 T1 和 T2 之间：
T1.5: 读请求发现缓存还在 → 返回旧值 "old_value"  ← 数据不一致！
```

**三种经典不一致场景**：

| 场景 | 描述 | 结果 |
|------|------|------|
| 先写后删 | 更新DB后缓存删除失败 | DB新、缓存旧 |
| 先删后写 | 删除缓存后更新DB失败 | DB旧、缓存旧 |
| 主从不一致 | 删缓存后从库还没同步完 | 旧数据回填缓存 |

### 20.2 Cache-Aside（旁路缓存）

**读流程**：
```
查缓存 → 命中 → 返回
       ↓ 未命中
查数据库 → 返回 + 写缓存
```

**写流程（标准做法）**：
```
方案A：先更新DB，再删缓存（推荐）
更新DB → 删缓存（不是更新缓存！）

方案B：先删缓存，再更新DB
删缓存 → 更新DB
```

**为什么删缓存而不是更新缓存？**

```
更新缓存可能失败：        删除缓存失败：
  DB=新值                  DB=新值
  缓存=旧值（更新失败）      缓存未删除
  → 不一致                  → 下次读会从DB加载，自动修复
                            → 最多短暂不一致
```

### 20.3 延时双删（Delay Double Delete）

#### 20.3.1 适用场景

解决**主从不一致**问题：删缓存后，从库还没同步完，从库读到了旧数据并回填缓存。

```
标准 Cache-Aside 问题：
  T1: 更新DB（主库）data = "new"
  T2: 删除缓存
  T3: 读请求 → 从库（还没同步）返回 data = "old" → 回填缓存 → 缓存变成"old"
  T4: 从库同步完成 → data = "new"
结果：缓存是"old"，数据库是"new"
```

#### 20.3.2 延时双删实现

```java
public void updateAndDeleteCache(String key, String newValue) {
    // 第一次删除缓存
    redisTemplate.delete(key);

    // 更新数据库（主库）
    database.update(key, newValue);

    // 延迟N秒后再次删除缓存（异步）
    // 等待主从不一致窗口过去
    CompletableFuture.runAsync(() -> {
        try {
            Thread.sleep(500);  // 等待主从同步完成（通常<500ms）
            redisTemplate.delete(key);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
}
```

**延时双删的时序**：

```
T1: 删除缓存
T2: 更新DB（主库）
T3: 延迟N毫秒后，再次删除缓存 ← 关键！
      ↑
      如果T1~T3之间有读请求从从库读到旧数据并回填缓存
      这步会把回填的旧缓存删掉
T4: 从库同步完成
结果：缓存被删除，下次读会从主库加载新值 → 一致
```

#### 20.3.3 延时双删的参数选择

| 参数 | 选择依据 | 常见值 |
|------|---------|--------|
| 延迟时间 | 主从同步延迟，通常几百毫秒 | 300-1000ms |
| 延迟是否随机 | 避免多请求同时删除造成雪崩 | `300 + random(200)` |
| 第二次删除失败 | 不重试，下次读自动修复 | 忽略 |

**建议配置**：
```java
private static final int BASE_DELAY_MS = 300;
private static final int RANDOM_DELAY_MS = 200;

public void delayDeleteCache(String key) {
    try {
        Thread.sleep(BASE_DELAY_MS + new Random().nextInt(RANDOM_DELAY_MS));
    } catch (InterruptedException e) {
        return;
    }
    redisTemplate.delete(key);
}
```

### 20.4 Binlog 订阅方案（Canal）

#### 20.4.1 为什么需要 Canal

延时双删是"主动"方案，需要业务代码配合。Canal是"被动"方案，通过监听数据库变更日志自动同步缓存。

```
MySQL 主库
    │
    │ 写入数据，生成 binlog 日志
    ▼
Canal Server（伪装成从库）  ← 监听 binlog
    │
    │ 解析 binlog，提取数据变更
    ▼
消息队列（MQ）
    │
    │ 广播到所有订阅者
    ▼
缓存更新服务  ← 收到消息，更新 Redis
```

#### 20.4.2 Canal + MQ 实现

```java
// 1. Canal 伪从库配置
canal:
  server: 127.0.0.1:11111
  destination: example
  filter: regex=.*\\..*
 subscribe: mysql-bin.001

// 2. Canal 客户端（消费 binlog 变更）
@RabbitListener(queues = "cache.sync")
public void handleCacheSync(CanalMessage message) {
    String tableName = message.getTable();      // 表名
    String operation = message.getOperation();     // INSERT/UPDATE/DELETE
    Object pkValue = message.getPkValue();        // 主键值
    Object data = message.getData();             // 变更数据

    String cacheKey = tableName + ":" + pkValue;

    switch (operation) {
        case "INSERT":
        case "UPDATE":
            redisTemplate.opsForValue().set(cacheKey, serialize(data));
            break;
        case "DELETE":
            redisTemplate.delete(cacheKey);
            break;
    }
}
```

#### 20.4.3 对比延时双删 vs Canal

| 维度 | 延时双删 | Canal + MQ |
|------|---------|-----------|
| 实现复杂度 | 低，几行代码 | 高，需要部署Canal集群 |
| 实时性 | 高，写操作时同步删缓存 | 高，binlog实时推送 |
| 可靠性 | 延迟时间固定，可能不够 | 可靠，只要MQ不丢消息 |
| 适用场景 | 少量缓存更新 | 大量缓存更新、跨服务更新 |
| 缺点 | 延迟时间靠猜，可能不准 | 需要额外组件 |
| 数据范围 | 只更新被业务代码覆盖的缓存 | 可以更新所有表的缓存 |

### 20.5 项目中的缓存一致性方案

你项目中的三种模式：

#### 方案一：本地缓存 + TTL（DatasetServiceImpl）

### 20.6 四种一致性方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| Cache-Aside | 读先缓存写先DB删缓存 | 简单，最常用 | 写后缓存旧数据 | 读多写少 |
| 延时双删 | Cache-Aside + 延迟再删一次 | 解决主从不一致 | 延迟时间固定不可靠 | 有主从同步场景 |
| 订阅binlog | Canal监听变更，主动更新缓存 | 实时性好，可靠 | 需要额外组件 | 数据一致性要求高 |
| L1+L2双层 | 本地缓存+Redis，本地优先 | 性能最优 | 多实例不同步 | 多实例部署 |
| Write-Through | 写缓存时同步写DB | 强一致 | 性能差 | 强一致性要求 |

### 20.7 面试回答模板

**问：缓存和数据库一致性问题怎么解决？**

> 有四种主流方案，根据场景选择：
>
> **Cache-Aside（旁路缓存）**：读先缓存、写先DB删缓存。核心是"删缓存而不是更新缓存"，因为更新缓存失败会导致DB新缓存旧，而删缓存失败了下次读自动修复。
>
> **延时双删**：解决主从不一致的问题。写操作后先删缓存、更新DB、延迟几百毫秒后再删一次缓存。这样即使从库还没同步完成时有读请求回填了旧缓存，第二次删除也会把旧缓存清掉。
>
> **订阅binlog**：用Canal伪装成从库监听MySQL binlog，数据变更后通过MQ通知所有消费者更新缓存。实时性最好，但需要部署额外组件。
>
> 我们的项目用Cache-Aside模式，读多用Redis做缓存，5分钟过期。写入时更新DB后删缓存。问题是外部API数据变更时缓存不主动失效，目前靠TTL过期自然失效。

**问：为什么删除缓存而不是更新缓存？**

> 因为更新缓存有两个风险：一是更新缓存失败了，DB是新值缓存是旧值，数据不一致；二是多实例部署时，先更新缓存再更新DB，第二个实例也在更新，可能覆盖第一个实例的更新。删除缓存失败了没关系，下次读的时候从DB加载新数据到缓存，最多短暂不一致。这是"宁可慢不要错"的思路。

**问：延时双删的延迟时间怎么定？**

> 一般设为主从同步延迟的1-2倍，常见300-1000ms。如果业务对一致性要求高，可以加随机抖动（300+random(200)ms），避免多个请求同时删除造成雪崩。更可靠的方案是用Canal订阅binlog，不依赖固定延迟时间。

## 二十一、日志实现原理

### 21.1 项目中的两种日志实现

#### 21.1.1 MDC（Mapped Diagnostic Context）— 日志链路追踪

**用途**：在日志中携带 traceId、userId 等上下文信息，实现全链路追踪。

```java
// MDC 的实现原理：ThreadLocal 存储上下文
public class MDC {
    private static final ThreadLocal<Map<String, String>> context =
        new ThreadLocal<>();

    public static void put(String key, String value) {
        Map<String, String> map = context.get();
        if (map == null) {
            map = new HashMap<>();
            context.set(map);
        }
        map.put(key, value);
    }

    public static String get(String key) {
        Map<String, String> map = context.get();
        return map == null ? null : map.get(key);
    }
}
```

**在项目中的应用**：

```java
// Filter 中设置 traceId
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(...) {
        String traceId = UUID.randomUUID().toString();
        MDC.put("traceId", traceId);  // 放入上下文
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.clear();  // 清理
        }
    }
}

// TaskDecorator 中传递到异步线程
public class FullContextTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();  // 主线程捕获
        return () -> {
            try {
                MDC.setContextMap(contextMap);  // 子线程恢复
                runnable.run();
            } finally {
                MDC.clear();  // 清理
            }
        };
    }
}
```

**AsyncAppender 的异步日志原理**：

```java

// 1. 主线程将日志放入阻塞队列
// 2. 后台线程从队列取日志，写入文件
// 3. 如果队列满了（默认容量256），主线程阻塞或丢弃
```

- 队列满时，主线程会阻塞等待（或丢弃日志，取决于配置）

### 21.3 日志规范与最佳实践

#### 日志级别使用规范

| 级别 | 含义 | 使用场景 |
|------|------|----------|
| ERROR | 错误，影响功能 | 异常捕获后打印，需要处理的错误 |
| WARN | 警告，可能有问题 | 降级逻辑、超时、参数不合法 |
| INFO | 信息，正常流程 | 接口入参出参、关键业务节点 |
| DEBUG | 调试，开发用 | 开发阶段打印变量值、流程分支 |
| TRACE | 跟踪，最详细 | 非常详细的调试信息 |

**项目中典型用法**：


### 21.4 面试回答模板

**问：MDC 是怎么实现日志链路追踪的？**

> MDC 底层是基于 ThreadLocal 实现的。每个线程有独立的 Map 存储 key-value，在 Filter 中设置 traceId 到 MDC，Logback 输出时通过 `%X{traceId}` 占位符从 ThreadLocal 中读取并输出。但普通 ThreadLocal 不能跨线程传递，所以需要用 TaskDecorator 在主线程中 `MDC.getCopyOfContextMap()` 捕获，再在子线程中 `MDC.setContextMap()` 恢复，这样异步日志也能带上 traceId。

**问：异步日志（AsyncAppender）的原理是什么？有什么坑？**

> AsyncAppender 内部有一个阻塞队列（默认256条），主线程打印日志时实际是放入队列，由后台专门的日志线程从队列取日志写入文件。好处是日志输出不阻塞主线程。坑有三个：一是队列满了主线程会阻塞（取决于discardingThreshold配置）；二是日志有延迟，因为是后台线程异步写；三是 `includeCallerData` 会保留调用行号，但性能损耗很大，生产环境建议关闭。

## 二十二、生产异常排查：没有堆栈怎么查

### 22.1 问题描述

```
生产环境异常，但日志只有：
java.lang.NullPointerException
    at xxx.xxx.Class.method(Class.java:123)  ← 这是有堆栈的

vs

java.lang.NullPointerException  ← 这是没有堆栈的，只有异常类型
```

**常见原因**：

| 原因 | 说明 |
|------|------|
| **异常被 `e.printStackTrace()`** | 生产环境 `System.err` 重定向到日志，但只打印了 toString，没打堆栈 |
| **异常被吞掉后重新抛** | catch 后 throws new RuntimeException(e)，没有设置 cause |
| **自定义异常没有堆栈** | 继承 Exception 但没调用 super(msg)，或调用了 fillInStackTrace() |
| **日志异步写丢失** | AsyncAppender 队列满，日志被丢弃 |
| **日志级别过滤** | WARN/INFO 级别不打印堆栈，只有 ERROR 才打 |
| **压缩/截断日志** | 日志收集组件（如 Filebeat）压缩或截断了长日志 |
| **多实例日志不完整** | 日志分布在多个机器，只看了部分日志 |

### 22.2 快速排查步骤

#### 第一步：确认异常是否真的没有堆栈

```java
// ❌ 错误：只打印了异常对象，没有堆栈
log.error("发生异常", e);              // e.printStackTrace() 只会打印 e.toString()
log.error("发生异常：" + e);            // 字符串拼接，同样没有堆栈

// ✅ 正确：让 Logback 自己格式化
log.error("发生异常：{}", e.getMessage(), e);  // 第三个参数是 Throwable，Logback会打印完整堆栈
log.error("发生异常", e);                       // 直接传 Throwable 对象
```

**Logback 配置**：确保异常被正确输出

```xml
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <encoder>
        <!-- %ex 或 %ex{short} 控制异常堆栈输出 -->
        <pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n</pattern>
    </encoder>
</appender>
<!-- 异常会跟在消息后面自动打印 -->
```

#### 第二步：增加更详细的日志

```java
// 增加关键变量日志，辅助定位
try {
    doSomething(param1, param2);
} catch (Exception e) {
    // 打印所有相关参数
    log.error("业务异常，param1={}, param2={}, userId={}, sessionId={}",
        param1, param2, userId, sessionId, e);
    // 打印当前上下文
    log.error("当前上下文，cookie={}, authContext={}",
        CookieContextHolder.getCookie(), AuthContext.getCurrentUser(), e);
    // 打印内存状态
    log.warn("内存状态，free={}MB, total={}MB",
        Runtime.getRuntime().freeMemory() / 1024 / 1024,
        Runtime.getRuntime().totalMemory() / 1024 / 1024);
}
```

#### 第三步：添加"心脏监控"日志（方法入口出口）

```java
// 切面实现，记录方法入参和出参
@Aspect
@Component
public class MethodLoggingAspect {

    @Around("execution(* cn.c4ai.dataset..service..*(..))")
    public Object logMethod(ProceedingJoinPoint pjp) throws Throwable {
        String methodName = pjp.getSignature().toShortString();
        Object[] args = pjp.getArgs();

        log.info("[ENTER] {}({})", methodName, Arrays.toString(args));

        long start = System.currentTimeMillis();
        Object result = null;
        Exception thrown = null;

        try {
            result = pjp.proceed();
            return result;
        } catch (Exception e) {
            thrown = e;
            throw e;
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (thrown != null) {
                log.error("[EXIT-EXCEPTION] {} took {}ms, threw {}",
                    methodName, cost, thrown.getClass().getSimpleName(), thrown);
            } else {
                log.info("[EXIT] {} took {}ms, result={}",
                    methodName, cost,
                    result == null ? "null" : result.getClass().getSimpleName());
            }
        }
    }
}
```

### 22.3 测试环境无法复现怎么办

### 22.4 面试回答模板

**问：生产异常没有堆栈怎么排查？**

> 首先要确认是不是日志打印方式的问题。`log.error(e)` 如果放在字符串拼接里（如 `log.error("error" + e)`），只会打印 e.toString()，不会有堆栈。正确做法是 `log.error("msg", e)` 直接把 Throwable 对象传进去，Logback 会自动格式化完整堆栈。
>
> 排查思路是三步走：第一步加日志，在异常处打印所有相关参数（traceId、userId、请求参数），以及上下文（cookie、当前线程名）；第二步用 Arthas 的 stack/trace/monitor 命令在生产环境attach进程，实时观察方法调用；第三步如果还查不出来，可以加一个 debug 开关，动态开启详细日志或者开启心脏监控切面，记录每个方法入口出口的入参和耗时。

**问：测试环境无法复现的bug怎么处理？**

> 这种问题往往是并发、时序或环境相关的。解决方案是：1）加详细日志，特别是关键分支点和异步任务的开始结束；2）用 Arthas 在生产环境诊断，不用复现就能看到方法调用；3）如果是并发问题，加线程安全的日志打印，比如 traceId 贯穿整个链路，这样可以从日志中还原请求的执行路径；4）加灰度开关，生产环境也可以通过配置中心动态开启详细日志。

## 二十三、Stream 流实战：两个列表按两个字段匹配

### 23.1 需求场景

```java
// 列表A：用户信息
List<User> userList = Arrays.asList(
    new User(1L, "张三", 25, "北京"),
    new User(2L, "李四", 30, "上海"),
    new User(3L, "王五", 28, "深圳")
);

// 列表B：订单信息
List<Order> orderList = Arrays.asList(
    new Order(100L, 1L, "商品A"),   // userId=1，张三的订单
    new Order(101L, 2L, "商品B"),   // userId=2，李四的订单
    new Order(102L, 1L, "商品C")    // userId=1，张三的另一个订单
);

// 需求：找出两个列表中，userId 和 age 都相同的记录 → (张三订单A, 张三订单C)
// 或者更常见：把两个列表按 userId 关联，返回匹配结果
```

### 23.2 常用场景及写法

#### 场景一：按单个字段匹配（最常见）

```java
// 需求：把 userList 和 orderList 按 userId 关联
// 结果：每个订单带上对应的用户信息

Map<Long, User> userMap = userList.stream()
    .collect(Collectors.toMap(User::getId, u -> u));

List<OrderWithUser> result = orderList.stream()
    .map(order -> {
        User user = userMap.get(order.getUserId());
        return new OrderWithUser(order, user);
    })
    .filter(owu -> owu.getUser() != null)  // 可能有无匹配的
    .collect(Collectors.toList());
```

#### 场景二：按两个字段匹配

```java
// 需求：找出 userList 和 orderList 中，userId 和地区（address）都相同的记录

// 方法1：嵌套循环（直观但 O(n²)）
List<MatchResult> result = userList.stream()
    .flatMap(user -> orderList.stream()
        .filter(order -> order.getUserId().equals(user.getId())
                     && order.getAddress().equals(user.getAddress()))
        .map(order -> new MatchResult(user, order)))
    .collect(Collectors.toList());

// 方法2：先按 userId 分组，再过滤（更高效）
Map<Long, List<User>> userByIdMap = userList.stream()
    .collect(Collectors.groupingBy(User::getId));

Map<Long, List<Order>> orderByIdMap = orderList.stream()
    .collect(Collectors.groupingBy(Order::getUserId));

List<MatchResult> result = userByIdMap.entrySet().stream()
    .filter(e -> orderByIdMap.containsKey(e.getKey()))
    .flatMap(e -> {
        List<User> users = e.getValue();
        List<Order> orders = orderByIdMap.get(e.getKey());
        return users.stream()
            .flatMap(user -> orders.stream()
                .filter(order -> user.getAddress().equals(order.getAddress()))
                .map(order -> new MatchResult(user, order)));
    })
    .collect(Collectors.toList());
```

#### 场景三：找出在一个列表中但不在另一个列表的记录

```java
// 需求：找出有订单的用户（在 orderList 中出现过的 userId）
Set<Long> userIdsWithOrder = orderList.stream()
    .map(Order::getUserId)
    .collect(Collectors.toSet());

List<User> usersWithOrder = userList.stream()
    .filter(user -> userIdsWithOrder.contains(user.getId()))
    .collect(Collectors.toList());

// 或者：找出没有订单的用户
List<User> usersWithoutOrder = userList.stream()
    .filter(user -> !userIdsWithOrder.contains(user.getId()))
    .collect(Collectors.toList());
```

#### 场景四：两列表的交集（按多个字段）

```java
// 需求：找出 userId 和 address 都相同的用户

Set<String> keysA = userList.stream()
    .map(u -> u.getId() + "_" + u.getAddress())
    .collect(Collectors.toSet());

List<User> intersection = orderList.stream()
    .map(o -> new User(o.getUserId(), o.getAddress()))
    .filter(u -> keysA.contains(u.getId() + "_" + u.getAddress()))
    .collect(Collectors.toList());

// 更优雅的写法：自定义 key 类
record UserKey(Long id, String address) {}

Set<UserKey> userKeys = userList.stream()
    .map(u -> new UserKey(u.getId(), u.getAddress()))
    .collect(Collectors.toSet());

List<Order> matched = orderList.stream()
    .filter(o -> userKeys.contains(new UserKey(o.getUserId(), o.getAddress())))
    .collect(Collectors.toList());
```

#### 场景五：保留列表A中，去掉列表B中存在的记录（按两个字段）

```java
// 需求：从 userList 中剔除那些在 blacklist 中有匹配的用户（id + address 相同）

Set<UserKey> blacklistKeys = blacklist.stream()
    .map(u -> new UserKey(u.getId(), u.getAddress()))
    .collect(Collectors.toSet());

List<User> filtered = userList.stream()
    .filter(user -> !blacklistKeys.contains(
        new UserKey(user.getId(), user.getAddress())))
    .collect(Collectors.toList());
```

### 23.3 性能优化：O(n²) → O(n)

```java
// ❌ O(n²)：每个 user 遍历 orderList
userList.stream()
    .flatMap(user -> orderList.stream()
        .filter(order -> order.getUserId().equals(user.getId())
                     && order.getAddress().equals(user.getAddress()))
        .map(order -> new MatchResult(user, order)))
    .collect(Collectors.toList());

// ✅ O(n)：先建 Map，再查
Map<String, List<Order>> orderMap = orderList.stream()
    .collect(Collectors.groupingBy(o -> o.getUserId() + "_" + o.getAddress()));

List<MatchResult> result = userList.stream()
    .map(user -> orderMap.get(user.getId() + "_" + user.getAddress()))
    .filter(Objects::nonNull)
    .flatMap(orders -> orders.stream()
        .map(order -> new MatchResult(user, order)))
    .collect(Collectors.toList());
```

### 23.4 面试回答模板

**问：两个列表按两个字段匹配，用 Stream 怎么写？**

> 按两个字段匹配的核心思路是**把字段合成一个 key**，用 Map 优化性能避免 O(n²)。
>
> ```java
> // 用 record 定义复合key（Java 16+）
> record UserOrderKey(Long id, String address) {}
>
> // 先把列表B转成 Map<key, list>
> Map<UserOrderKey, List<Order>> orderMap = orderList.stream()
>     .collect(Collectors.groupingBy(o -> new UserOrderKey(o.getUserId(), o.getAddress())));
>
>
> // 再遍历列表A去查
> List<MatchResult> result = userList.stream()
>     .map(user -> orderMap.get(new UserOrderKey(user.getId(), user.getAddress())))
>     .filter(Objects::nonNull)
>     .flatMap(orders -> orders.stream().map(order -> new MatchResult(user, order)))
>     .collect(Collectors.toList());
> ```
>
> 关键点是**不要嵌套循环 stream()**，那样是 O(n²) 性能很差。先把其中一个列表转成 Map，key 是两个字段拼接的字符串或 record 对象，再查 Map 就是 O(1)，整体变成 O(n)。
