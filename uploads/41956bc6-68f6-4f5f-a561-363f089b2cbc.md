### 1.2 模块职责划分

| 模块 | 端口 | 技术 | 职责 |
|------|------|------|------|
| **inpcs-rest** | 10025 | Spring MVC + Dubbo Consumer | HTTP接口层，接收前端请求，通过@Reference调用远程服务 |
| **inpcs-server** | 10024 | Spring Boot + Dubbo Provider | 业务逻辑层，@Service发布Dubbo服务 |
| **inpcs-core** | - | SSM (MyBatis) | 实体类、Mapper接口、Service接口 |
| **inpcs-web** | - | JSP | 大屏展示 |

### 1.3 为什么这样分层

**面试回答：**
> "项目采用标准的四层架构，分层的好处是**职责分离、便于维护**。inpcs-rest作为HTTP入口层，只负责接收请求和返回响应，不写业务逻辑；inpcs-server作为业务逻辑层，聚合各种服务调用；inpcs-core作为数据访问层，专注数据库操作。这样分层后，如果要改接口协议（比如从REST改成GraphQL），只需要改rest层，不会影响业务逻辑。Dubbo在这一层的作用是把RPC调用对上层透明化，Controller调用ConsumeService时，感觉像在调用本地方法，实际上是跨JVM的远程调用。"

## 二、Dubbo + Zookeeper 分布式RPC

### 2.1 背景

在传统单体应用中，所有代码在一个JVM中运行，方法调用是直接的内存调用。但随着业务增长，单体应用面临：
- **代码耦合严重**：一个模块的改动可能影响整个系统
- **部署不灵活**：只能整体部署，无法按模块独立发布
- **扩展困难**：无法针对瓶颈模块单独扩展
- **团队协作难**：多人同时改一个代码库，冲突频繁

因此需要将系统拆分为多个独立部署的服务，服务间通过RPC（远程过程调用）通信。

### 2.2 原理

#### 2.2.1 Dubbo工作原理

```
┌─────────────────────────────────────────────────────────────────────┐
│                           Dubbo工作流程                              │
│                                                                      │
│  Consumer侧:                                                         │
│  ┌────────────┐    ┌────────────┐    ┌────────────┐    ┌─────────┐ │
│  │  Consumer  │→   │ Directory  │→   │  Cluster   │→   │ Load    │ │
│  │  (调用方)   │    │ (服务目录)  │    │ (负载均衡)  │    │ Balance │ │
│  └────────────┘    └────────────┘    └────────────┘    └─────────┘ │
│         ↑               ↑                                         │
│         │               │ 从Zookeeper获取Provider列表              │
│         │               ▼                                         │
│         │         ┌────────────┐                                   │
│         │         │ Registry   │←──订阅/通知──→ Zookeeper          │
│         │         │ (注册中心)  │                                   │
│         │         └────────────┘                                   │
│         │                                                         │
│  ┌──────┴───────────────────────────────────────────────────────┐  │
│  │                     Filter链 (可选)                           │  │
│  │  监控统计 │ 访问日志 │ 权限校验 │ 超时控制 │ 限流熔断 │ ...    │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │                    Dubbo协议层 (可切换)                        │  │
│  │  Dubbo协议(默认) │ RMI │ Hessian │ HTTP │ WebService │ ...   │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  Provider侧:                                                        │
│  ┌────────────┐    ┌────────────┐    ┌────────────┐                │
│  │  Provider  │←   │   Export   │←   │  Registry  │                │
│  │  (服务方)   │    │ (服务暴露)  │    │ (注册中心)  │                │
│  └────────────┘    └────────────┘    └────────────┘                │
└─────────────────────────────────────────────────────────────────────┘
```

#### 2.2.2 Zookeeper在Dubbo中的作用

Zookeeper是一个**分布式协调服务**，在Dubbo中扮演**服务注册与发现**的角色：

1. **服务注册**：Provider启动时，向Zookeeper注册自己的地址信息
2. **服务订阅**：Consumer启动时，向Zookeeper订阅自己需要的服务
3. **动态感知**：当Provider新增或下线时，Zookeeper通知Consumer更新本地缓存

```
Zookeeper存储结构示例：
/dubbo
  └── com.enjoyor.soa.traffic.api.service.dubbo.inpcs.IDubboOrdersInfoService
        ├── providers
        │     ├── dubbo://192.168.91.124:22322/com.enjoyor...  ← Provider地址
        │     └── dubbo://192.168.91.125:22322/com.enjoyor...  ← 另一个Provider
        ├── consumers
        │     └── consumer://192.168.91.126:54321/com.enjoyor...  ← Consumer地址
        └── configurators
              └── override://0.0.0.0/com.enjoyor...  ← 动态配置（可修改权重等）
```

#### 2.3.3 代码示例

**Provider端发布服务（DubboOrdersInfoServiceImpl.java）：**

```java
// 使用Dubbo的@Service注解（非Spring的），发布到注册中心
@Service
public class DubboOrdersInfoServiceImpl implements IDubboOrdersInfoService {

    @Autowired
    private ManageOrdersInfoService manageOrdersInfoService;

    @Override
    public ResultPojo selectOrdersInfoById(String ordersId) {
        // 业务逻辑处理
        return manageOrdersInfoService.selectOrdersInfoById(ordersId);
    }
}
```

**Consumer端引用服务（OrdersInfoConsumeService.java）：**

```java
@Component
public class OrdersInfoConsumeService {

    // timeout设置100秒，因为复杂查询可能耗时较长
    @Reference(timeout = 100000)
    private IDubboOrdersInfoService dubboOrdersInfoService;

    public ResultPojo selectOrdersInfoById(String ordersId) {
        // 像调用本地方法一样调用远程服务
        return dubboOrdersInfoService.selectOrdersInfoById(ordersId);
    }
}
```

### 2.4 为什么选Dubbo而不是其他方案

| 方案 | 优点 | 缺点 | 为什么选Dubbo |
|------|------|------|-------------|
| **Dubbo** | 高性能（TCP长连接）、成熟的生态、完善的监控 | 学习成本 | 项目是内部系统间调用，性能优先；SSM架构对XML配置支持好 |
| **Feign** | 轻量、与Spring Cloud集成好 | 基于HTTP，性能较低 | 政务项目用SSM，引入Spring Cloud成本高 |
| **gRPC** | 高性能、跨语言 | 需要定义proto文件 | 纯Java项目，不需要跨语言 |
| **HTTP Client** | 简单直接 | 没有服务治理功能 | 无法做负载均衡、熔断、服务发现 |

**面试回答：**
> "选择Dubbo主要基于三点考虑：1）**性能**：Dubbo基于TCP长连接，序列化效率比HTTP高很多，适合内部高并发调用；2）**成熟度**：Dubbo在国内有大量使用案例，文档完善，社区活跃；3）**服务治理**：自带负载均衡、熔断、限流等服务治理能力，不需要额外集成组件。"

### 2.5 解决了什么问题

1. **服务拆分与独立部署**：民情管理、用户管理、统计分析等模块可以独立发布，不影响其他模块
2. **团队并行开发**：不同团队负责不同服务，并行开发效率高
3. **弹性扩展**：高峰期可以对工单服务单独扩容
4. **故障隔离**：一个服务挂了不会导致整个系统不可用

### 2.6 踩过的坑与优化

**坑1：Dubbo超时时间设置不当**
```java
// 问题：默认超时只有1秒，复杂查询经常超时
@Reference  // 默认timeout=1000

// 解决：根据业务场景设置合理的超时时间
@Reference(timeout = 100000)  // 100秒，适用于分页查询等耗时操作
```

**坑2：Zookeeper连接超时**
```properties
# 问题：Zookeeper网络抖动时，服务调用失败
# 解决：增加超时时间，并配置重试机制
spring.dubbo.registry.timeout=180000
```

**优化：Dubbo负载均衡策略**
```java
// 在多Provider环境下，选择合适的负载均衡策略
// 随机（默认）| 轮询 | 最少活跃调用 | 一致性哈希
// 项目中使用了默认的随机策略，在实际使用中表现良好
```

## 三、SSO单点登录 + Token认证

### 3.1 背景

政务系统通常有多个子系统（如民情管理、代表管理、智联站管理等），如果每个系统都独立做登录，用户需要在每个系统中注册账号，既不方便也不安全。因此需要**单点登录（SSO）**——用户只需登录一次，就可以访问所有有权限的系统。

### 3.2 原理

#### 3.2.1 SSO整体流程

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              SSO认证流程                                     │
│                                                                             │
│  首次访问:                                                                   │
│  ┌────────┐        ┌──────────┐        ┌────────────┐       ┌───────────┐ │
│  │ 用户   │───→    │ SSO Filter │───→   │ SSO Server │───→   │ 登录页面  │ │
│  │ 浏览器  │        │ 拦截请求   │        │  (无Token) │       │ (输入账号) │ │
│  └────────┘        └──────────┘        └────────────┘       └───────────┘ │
│       │                                                                   │
│       │ 输入账号密码                                                          │
│       ▼                                                                   │
│  ┌────────────┐        ┌──────────┐        ┌────────────┐                  │
│  │ SSO Server │───→    │ 生成Token │───→   │ Token写入   │                  │
│  │ (认证通过)  │        │ 返回Cookie│        │ 用户浏览器  │                  │
│  └────────────┘        └──────────┘        └────────────┘                  │
│                                                                             │
│  后续访问:                                                                   │
│  ┌────────┐        ┌──────────┐        ┌────────────┐       ┌───────────┐ │
│  │ 用户   │───→    │ SSO Filter │───→   │ Token验证   │───→   │ 业务接口  │ │
│  │ 浏览器  │        │ 携带Cookie │        │  (有效)    │       │  (放行)   │ │
│  └────────┘        └──────────┘        └────────────┘       └───────────┘ │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 3.2.2 Token验证机制

用户登录后，SSO Server生成一个Token（通常是JWT或随机字符串），返回给客户端。以后每次请求，客户端携带这个Token，SSO Filter调用SSO Server验证Token有效性。

```
Token包含的信息（JWT格式示例）：
{
  "sub": "person_12345",      // 用户ID
  "name": "张三",              // 用户名
  "roles": ["代表", "联络站"], // 角色列表
  "orgId": "t310030",         // 组织ID
  "exp": 1699999999,          // 过期时间
  "iss": "uums-server"        // 签发者
}
```

### 3.3 项目中的实际配置

#### 3.3.1 SSO配置文件

```properties
# SSO过滤器配置（application-dev.properties）

# 启用SSO
sso.client.filter[startUp]=1

# SSO认证服务器地址
sso.client.filter[server]=http://192.168.91.124:10002/uums3-rest/

# Token验证接口（检查Token是否有效）
sso.client.filter[checkUrl]=http://192.168.91.124:10002/uums3-rest/token/check

# 系统标识Key（用于区分不同子系统）
sso.client.filter[systemKey]=f337bdf1-3537-4687-91a1-92538555521d

# 拦截规则：所有HTML请求都需要验证
sso.client.filter[urlPatterns]=*.html

# 排除路径：公开接口不需要登录
sso.client.filter[excludePaths]=/**/ordersRecord/fackbackOrdersFour/**,\
  /**/ordersRecord/fackbackEvent/**,\
  /**/ordersPublic/applyOrdersInfoByPublic/**,\
  /**/fileLocal/uploadFile/**,\
  /**/selectSingleOrdersPage/**
```

#### 3.3.2 排除路径详解

以下接口不需要登录即可访问：

| 路径 | 说明 | 为什么不需要登录 |
|------|------|----------------|
| `fackbackOrdersFour/**` | 四平台回调接口 | 四平台系统回调，不需要人为操作 |
| `ordersPublic/**` | 公众端接口 | 群众提交建议、查看进度等公开功能 |
| `fileLocal/uploadFile/**` | 文件上传 | 附件上传接口 |
| `selectSingleOrdersPage/**` | 大屏数据接口 | 大屏展示无需登录 |

### 3.4 为什么这样设计

**面试回答：**
> "SSO设计遵循两个原则：1）**最小权限**：只对需要保护的路径进行拦截，减少不必要的验证开销；2）**明确排除**：把公开接口和回调接口显式排除，避免外部系统回调时被拦截。实际配置中，我们将四平台回调、公众端、大屏展示等都排除在外，因为这些场景要么是系统间调用，要么本身就是公开的。"

### 3.5 获取登录用户信息

在业务代码中，通过 `UserDto` 获取当前登录用户：

```java
// OrdersInfoConsumeService.java 中的例子
public ResultPojo selectOrdersPageByMine(Page page, String type,
    String repContent, String repStartTime, String repEndTime,
    UserDto userDto, String streetId) {
    // 从UserDto获取当前登录用户信息
    String repPersonId = userDto.getPersonId();   // 获取用户ID
    String roleName = userDto.getRoleName();       // 获取角色名
    String orgId = userDto.getOrgId();             // 获取组织ID
    // 根据用户信息筛选数据
}
```

### 3.6 解决了什么问题

1. **用户体验**：一次登录，多系统访问
2. **安全性**：统一在SSO Server验证，避免各子系统密码泄露
3. **可控性**：可以在SSO Server统一管理用户权限
4. **审计**：所有登录操作集中在SSO，便于日志审计

## 四、HMAC-SHA256 签名认证（四平台对接）

### 4.1 背景

四平台对接（基层治理平台、事件中心等）需要与外部系统进行数据交换。为了防止：
- **数据篡改**：攻击者修改请求参数
- **伪造请求**：攻击者伪装成合法系统发起请求
- **重放攻击**：截获请求后重复发送

需要一套安全可靠的签名认证机制。

### 4.2 原理

#### 4.2.1 HMAC-SHA256签名原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
```

#### 4.2.2 为什么用HMAC-SHA256

| 方案 | 优点 | 缺点 | 为什么选HMAC-SHA256 |
|------|------|------|-------------------|
| **明文密码** | 简单 | 密码明文传输，极不安全 | ❌ |
| **Basic Auth** | 简单 | 用户名密码每次明文传输 | ❌ |
| **MD5签名** | 简单 | 易被碰撞攻击，不够安全 | 部分平台用 |
| **HMAC-SHA256** | 安全、不可逆、防篡改 | 实现稍复杂 | ✅ 主流方案 |
| **RSA签名** | 安全性更高 | 需要管理密钥对，计算量大 | 性能开销大 |

```java
private StringBuffer fourCommonFun(String operUrl, int randomStringLength,
    JSONObject paramJson, String ordersId, String queryParam, String requestMethod) {

    // 1. 生成随机字符串nonce（防重放）
    String nonce = randomString(randomStringLength);  // 如 "abc123XYZ"

    // 2. 按字母升序拼接查询参数（保证签名一致性）
    String queryContent = "appId=" + newFourAppid + queryParam
            + "&nonce=" + nonce
            + "&timestamp=" + (System.currentTimeMillis() / 1000)  // 时间戳
            + "&v=v1";

    // 3. HMAC-SHA256签名
    Security.addProvider(new BouncyCastleProvider());  // 添加加密提供者
    SecretKey secretKey = new SecretKeySpec(newFourSecret.getBytes("UTF8"), "HMacSHA256");
    Mac mac = Mac.getInstance(secretKey.getAlgorithm());
    mac.init(secretKey);
    // 签名内容 = 查询参数 + 请求体
    byte[] digest = mac.doFinal((queryContent + paramJson.toString()).getBytes("UTF-8"));
    String authorization = new HexBinaryAdapter().marshal(digest);

    // 4. 发送请求
    URL realUrl = new URL(operUrl + "?" + queryContent);
    HttpURLConnection conn = (HttpURLConnection) realUrl.openConnection();
    conn.setRequestMethod(requestMethod);
    conn.setRequestProperty("Content-Type", "application/json");
    conn.setRequestProperty("Authorization", authorization.toLowerCase());
    conn.connect();

    // 5. 读取响应
    // ...
}
```

### 4.5 解决了什么问题

2. **防止伪造身份**：没有secret无法生成正确签名

**坑1：签名不一致**
- **问题**：发送方和接收方拼接参数顺序不一致，导致签名不同

**坑2：时间戳格式不统一**
- **问题**：发送方用毫秒时间戳，接收方用秒时间戳
- **解决**：统一使用秒级时间戳 `(System.currentTimeMillis() / 1000)`

**坑3：中文编码问题**
- **问题**：中文参数签名后与接收方不一致
- **解决**：统一使用UTF-8编码

1. **用户体验**：短信发送是外部调用，耗时不确定，异步处理避免阻塞主业务

### 5.4 为什么这样设计

**面试回答：**
> "短信通知系统的设计核心是**操作类型与接收角色的精准匹配**。我们抽象出5类角色——申报人、联络站代表、联络站站长、智联站联络员、办理人员，以及12种操作类型。通过布尔参数组合的方式，实现了灵活的匹配逻辑。比如群众反映时，如果该联络站有代表，就发给代表；如果没配代表，就发给站长。这种设计的好处是新增操作类型时，只需要添加一个if-else分支，不需要改动核心逻辑。"

### 5.5 解决了什么问题

1. **精准通知**：不同操作通知不同角色，避免信息过载
2. **异步处理**：短信发送不阻塞业务流程
3. **去重机制**：HashSet防止同一用户收到重复短信
4. **拒收功能**：特殊用户可以选择不接收短信
5. **日志追溯**：每条短信发送都有记录，便于排查问题

### 5.6 踩过的坑与优化

**坑1：短信发送频率控制**
- **问题**：超时催办可能一天发多条，用户投诉
- **解决**：增加发送频率控制，同一用户同类型短信一天最多发一次

**坑2：手机号为空**
- **问题**：部分用户没有登记手机号
- **解决**：发送前检查手机号有效性，空号跳过不阻塞

**坑3：并发去重失效**
- **问题**：并发场景下HashSet不是线程安全的
- **解决**：使用ConcurrentHashMap或Collections.synchronizedSet

## 六、Druid监控 + 慢SQL定位与优化

### 6.1 背景

项目上线后，用户反馈系统慢。通过分析发现：
- **数据库是主要瓶颈**：政务系统大量关联查询，没有索引
- **慢SQL难以定位**：没有监控，不知道哪些SQL最耗时
- **连接池配置不当**：连接数不够用或浪费资源

### 6.2 原理

#### 6.2.1 Druid连接池工作原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         Druid连接池工作原理                                  │
│                                                                             │
│  连接池初始化（启动时）:                                                      │
│  ┌─────────────────────────────────────────────────────────────────────┐    │
│  │   initial-size=1 ───→ 创建1个初始连接                                │    │
│  │                                                                     │    │
│  │   ┌─────────┐ ┌─────────┐ ┌─────────┐                              │    │
│  │   │ 连接1   │ │ 连接2   │ │ 连接N   │  ←  连接池                    │    │
│  │   │ (空闲)  │ │ (空闲)  │ │ (空闲)  │                              │    │
│  │   └─────────┘ └─────────┘ └─────────┘                              │    │
│  └─────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  获取连接流程:                                                              │
│  ┌─────────────────────────────────────────────────────────────────────┐    │
│  │  1. 检查空闲连接                                                     │    │
│  │  2. 空闲连接 > minIdle，创建新连接                                   │    │
│  │  3. 空闲连接 = 0，等待（maxWait超时）                                 │    │
│  │  4. 空闲连接 = 0，超时 ──→ 抛异常                                    │    │
│  └─────────────────────────────────────────────────────────────────────┘    │
│                                                                             │
│  连接归还流程:                                                              │
│  ┌─────────────────────────────────────────────────────────────────────┐    │
│  │  1. 使用完后调用 connection.close()                                  │    │
│  │  2. 连接不关闭，放回空闲队列                                          │    │
│  │  3. 定时清理多余连接（超过minIdle的连接）                              │    │
│  └─────────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 6.2.2 Druid监控能力

| 监控类型 | 说明 | 面试亮点 |
|---------|------|---------|
| **SQL监控** | 每条SQL执行次数、平均耗时、最大耗时、并发数 | 可以定位TOP N慢SQL |
| **URI监控** | 每个接口的执行时间、并发数 | 可以定位慢接口 |
| **连接池监控** | 活跃连接、空闲连接、等待线程数、连接创建/销毁 | 可以发现连接泄漏 |
| **Spring监控** | Bean方法执行耗时 | 可以监控@Transactional |
| **Web监控** | URL访问、Session、错误页面 | 可以看用户行为 |
| **防火墙** | SQL注入防御、黑名单 | 安全防护 |

### 6.7 踩过的坑与优化

**坑1：连接泄漏**

- **发现**：Druid监控显示"连接使用中"数持续增加
- **解决**：确保使用try-with-resources或finally关闭连接

**坑2：Oracle到达梦方言差异**
- **问题**：达梦不支持Oracle的某些语法
- **解决**：配置 `hibernate.dialect=org.hibernate.dialect.OracleDialect`（达梦兼容模式）

## 七、Redis连接池配置

### 7.1 背景

项目中Redis主要用于：
- **会话缓存**：存放用户登录Token
- **热点数据缓存**：减少数据库压力
- **分布式锁**：多实例部署时的并发控制

### 7.2 项目中的实际配置

```properties
# Redis配置（application-dev.properties）
spring.redis.database=0
spring.redis.host=zhumin.pro
spring.redis.port=56379
spring.redis.password=12345

# 连接池配置
spring.redis.pool.maxActive=20    # 最大活跃连接数
spring.redis.pool.maxWait=-1     # 获取连接最大等待时间（-1表示无限等待）
spring.redis.pool.maxIdle=60     # 最大空闲连接数
spring.redis.pool.minIdle=8      # 最小空闲连接数
spring.redis.timeout=5000        # 连接超时5秒

spring.redis.isneedpassword=false
```

### 7.3 配置参数详解

| 参数 | 值 | 说明 | 为什么这样设置 |
|------|-----|------|---------------|
| maxActive | 20 | 最大连接数 | 根据并发量估算，避免过多连接耗尽资源 |
| maxIdle | 60 | 最大空闲连接 | 保持一定空闲连接，减少创建开销 |
| minIdle | 8 | 最小空闲连接 | 预热连接池，避免请求高峰时创建连接延迟 |
| maxWait | -1 | 获取连接等待时间 | 无限等待，由程序控制超时 |
| timeout | 5000 | 连接超时 | 网络情况决定，5秒足够 |

### 7.4 面试回答

> "Redis连接池配置的核心是**平衡性能与资源消耗**。maxActive=20是根据系统并发量估算的，政务系统并发量不高，20个连接足够。maxIdle=60和minIdle=8是为了保持连接预热状态，减少连接创建的开销。timeout=5000是因为Redis服务在本地网络，5秒内应该能建立连接。"

## 八、Kafka消费者（报警事件异步接入）

### 8.1 背景

系统需要接入海康、大华等视频监控设备的报警事件。如果采用同步调用：
- **耦合严重**：报警设备需要知道业务系统地址
- **性能差**：同步等待报警处理完成
- **不可靠**：报警设备无法重试

因此采用消息队列，报警设备只需发送到Kafka，业务系统异步消费。

### 8.2 原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          Kafka报警事件接入流程                               │
│                                                                             │
│  ┌──────────┐      ┌───────────┐      ┌────────────┐      ┌─────────────┐ │
│  │ 海康摄像头 │ ──→ │   Kafka   │ ──→  │  Kafka     │ ──→  │ 业务处理    │ │
│  │ 大华摄像头 │      │  消息队列  │      │  Consumer  │      │  (异步)     │ │
│  └──────────┘      └───────────┘      └────────────┘      └─────────────┘ │
│                                                                             │
│  Topic配置:                                                                 │
│  ┌─────────────────────────────────────────────────────────────────────┐  │
│  │  kafka.bootstrap-servers = 192.168.94.2:9099                         │  │
│  │  kafka.consumer.group.id = testWZ                                    │  │
│  │  kafka.consumer.topic.alarm.video = alarm_dahua     (大华视频报警)   │  │
│  │  kafka.consumer.topic.alarm.fire = alarm_fire        (消防报警)     │  │
│  │  kafka.consumer.topic.alarm.thermography = hikalarm  (海康热成像)   │  │
│  └─────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 8.3 项目中的实际配置

```properties
kafka.bootstrap-servers=192.168.94.2:9099
kafka.consumer.group.id=testWZ
kafka.consumer.topic.alarm.video=alarm_dahua
kafka.consumer.topic.alarm.fire=alarm_fire
kafka.consumer.topic.alarm.thermography=hikalarm
kafka.consumer.receive=true
kafka.consumer.start.frombegin=true
```

### 8.4 解决了什么问题

1. **解耦**：报警设备只发消息到Kafka，不需要知道业务系统地址
2. **削峰**：报警事件可能突发，Kafka作为缓冲
3. **可靠**：Kafka保证消息至少被消费一次
4. **异步**：不影响主业务处理

### 8.5 为什么选Kafka

| 特性 | Kafka | RabbitMQ | RocketMQ |
|------|-------|----------|----------|
| 吞吐量 | 百万级/秒 | 万级/秒 | 十万级/秒 |
| 消息持久化 | 支持 | 支持 | 支持 |
| 消息回溯 | 支持 | 不支持 | 支持 |
| 适用场景 | 日志采集、大数据 | 小消息、服务间异步 | 电商交易 |

> "政务系统的报警事件量不大，但需要可靠的持久化和回溯能力，Kafka正好满足需求。"

## 九、Oracle迁移达梦数据库（信创云改造）

2022年国家推进信息技术应用创新（信创），要求政府系统使用国产数据库。西湖区人大系统原使用Oracle，需要迁移到达梦（DM）数据库。

- 达梦（DM）是国产关系型数据库，兼容Oracle语法
- 支持Windows、Linux等多种操作系统
- 通过了等保三级、可信云等认证，适合政务场景

| 语法差异 | - | 部分函数、关键字差异 |

### 9.4 迁移过程中踩过的坑

#### 坑1：validation-query语法差异
```sql
-- Oracle
SELECT 'x' FROM DUAL

-- 达梦
SELECT 1 FROM DUAL
```

#### 坑2：日期函数差异
```sql
-- Oracle
SELECT TO_CHAR(SYSDATE, 'YYYY-MM-DD') FROM DUAL

-- 达梦（兼容）
SELECT TO_CHAR(SYSDATE, 'YYYY-MM-DD') FROM DUAL  -- 达梦也支持

-- 达梦特有
SELECT TO_DATE('2024-01-01', 'YYYY-MM-DD') FROM DUAL
```

#### 坑3：CLOB字段处理
```java
// Oracle可以直接用String
String content = ordersInfo.getRepContent();

// 达梦需要特殊处理（某些情况下）
// 如果内容为空，达梦CLOB可能返回null而不是空字符串
if (content == null) {
    content = "";
}
```

### 9.5 解决了什么问题

1. **符合信创要求**：使用国产数据库，通过信创测评
2. **数据安全**：达梦通过等保三级认证
3. **平滑迁移**：大部分SQL无需改动，迁移成本低

### 9.6 面试回答

> "信创云改造主要是Oracle迁移到达梦数据库。改动包括：1）**驱动替换**：从Oracle JDBC驱动换成达梦驱动Dm8JdbcDriver18；2）**URL格式变更**：从oracle:thin协议变为dm协议，端口从1521变为5236；3）**连接池校验SQL**：从`SELECT 'x'`改为`SELECT 1 FROM DUAL`；4）**Hibernate方言**：配置为OracleDialect（达梦兼容模式）；5）**SQL兼容性处理**：部分Oracle特有函数在达梦中需要替换。迁移过程中主要踩的坑是达梦对CLOB类型处理和部分日期函数的细微差异，通过代码兼容处理解决。"

## 十、流水号自动获取与状态同步

### 10.1 背景

工单系统需要与四平台（基层治理平台）对接。当工单在四平台办理完成后，四平台会生成一个流水号（类似身份证号，唯一标识）。系统需要自动获取这个流水号，并更新工单状态。

### 10.2 原理

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      流水号自动获取与状态同步流程                             │
│                                                                             │
│  ┌────────────┐    ┌────────────┐    ┌────────────┐    ┌────────────┐     │
│  │  工单系统   │───→│  数据资产   │───→│  四平台    │───→│  返回结果   │     │
│  │  发起查询   │    │   平台API  │    │  查询工单   │    │  解析流水号 │     │
│  └────────────┘    └────────────┘    └────────────┘    └────────────┘     │
│                                                                             │
│  数据流:                                                                    │
│  ┌─────────────────────────────────────────────────────────────────────┐  │
│  │  请求: {"PID": "W20240101123456789"}                                │  │
│  │  认证: clientId + clientSecret                                       │  │
│  │  响应: {"success": true, "data": [{"STATUS": "38", "SERIAL_NUMBER":  │  │
│  │        "ZX202401010001"}]}                                          │  │
│  └─────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  状态同步:                                                                  │
│  ┌─────────────────────────────────────────────────────────────────────┐  │
│  │  STATUS = "38"  ──→  办结状态  ──→  更新工单流水号字段                │  │
│  │  STATUS != "38" ──→  未办结   ──→  跳过，等待下次查询                 │  │
│  └─────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 10.3 项目中的实际代码

```java
@Transactional(rollbackFor = Exception.class)
public ResultPojo updateSerialNumberByOrdersId() {
    try {
        // 1. 查询所有需要获取流水号的工单
        ResultPojo resultPojo = ordersInfoService.getSerialNumberByOrdersId();
        List<OrdersInfo> ordersInfoList = (List<OrdersInfo>) resultPojo.getResultList();

        for (int i = 0; i < ordersInfoList.size(); i++) {
            OrdersInfo ordersInfo = ordersInfoList.get(i);

            // 2. 构造查询请求
            JSONObject eventDoneParam = new JSONObject();
            eventDoneParam.put("clientId", "base_n80n1xfpSdgMI_LdbDu1Fg");
            eventDoneParam.put("clientSecret", "ud3IyVxd6A07O3XyEWUdT0Cu5NFssXnIxrSpXykW4l2sh5LKEdazwB6p3vAYhRzr");
            eventDoneParam.put("pageNum", 1);
            eventDoneParam.put("pageSize", 10);
            eventDoneParam.put("dataMap", {"PID": ordersInfo.getOrdersId()});

            // 3. 调用数据资产平台API
            String findDataResult = GetPostUntil.doPostJson(findDataUrl, header,
                eventDoneParam.toJSONString());

            // 4. 解析响应
            if (success.equals("true")) {
                String SERIAL_NUMBER = map.get("SERIAL_NUMBER");
                String stateCode = String.valueOf(map.get("STATUS"));

                // 5. 状态码38表示办结，更新流水号
                if (stateCode.equals("38")) {
                    OrdersInfo upDateOrdersInfo = new OrdersInfo();
                    upDateOrdersInfo.setOrdersId(ordersInfo.getOrdersId());
                    upDateOrdersInfo.setSerialNumber(SERIAL_NUMBER);
                    ordersInfoService.updateSerialNumberByOrdersId(upDateOrdersInfo);
                }
            }
        }
        return ResultHelper.getResult(findDataResult);
    } catch (Exception e) {
        return ResultHelper.getResult(e);
    }
}
```

### 10.4 解决了什么问题

1. **自动化**：无需人工介入，系统自动同步流水号
2. **实时性**：工单办结后，流水号自动更新
3. **事务一致性**：@Transactional保证要么全部成功，要么全部回滚
4. **容错处理**：单个工单失败不影响其他工单

### 10.5 踩过的坑与优化

**坑1：API调用超时**

- **解决**：增加重试机制，超时后等待一段时间重试

**坑2：重复更新**
- **问题**：同一工单可能被多次查询到
- **解决**：工单表增加serial_number字段，已更新的不再重复调用

### 11.4 工单新增逻辑

```java
public ResultPojo insertOrdersInfo(OrdersDto ordersDto, String personName) {
    // 1. 参数校验
    if (StringUtils.isBlank(ordersDto.getRepPersonName())) {
        return ResultHelper.getResult(null, EnumAppCode.PARAM_NULL, "申报人姓名不能为空");
    }

    // 2. 构造工单对象
    OrdersInfo ordersInfo = ObjectSwitchHelper.ordersDtoToPojo(ordersDto);

    // 3. 生成工单ID（格式：W+时间戳+随机数）
    String ordersId = "W" + TimeHelper.dateToString(new Date(), "yyyyMMddHHmmssSSS")
                    + TimeHelper.genRandomNum(5);
    ordersInfo.setOrdersId(ordersId);

    // 4. 根据申报人身份确定初始状态
    String repPositionCode = ordersInfo.getRepPositionCode();
    if (EnumDicPublic.ORDERS_POSITION_MIN.getKey().equals(repPositionCode)      // 选民
     || EnumDicPublic.ORDERS_POSITION_OBSERVER.getKey().equals(repPositionCode) // 民情观察员
     || EnumDicPublic.ORDERS_POSITION_MASSES.getKey().equals(repPositionCode)) {// 群众
        ordersInfo.setStatusCode(EnumDicPublic.ORD_STATUS_APPLY.getKey());  // 新建议
    } else if (EnumDicPublic.ORDERS_POSITION_JING.getKey().equals(repPositionCode)    // 代表
            || EnumDicPublic.ORDERS_POSITION_FACE.getKey().equals(repPositionCode)) { // 面对面
        ordersInfo.setStatusCode(EnumDicPublic.ORD_STATUS_REPORT.getKey());   // 已上报
    }

    // 5. 插入工单
    ordersInfoService.insertOrdersInfo(ordersInfo);

    // 6. 创建操作记录
    OrdersRecordInfo ordersRecordInfo = new OrdersRecordInfo(
        ordersId, operTypeCode, operExplain,
        ordersInfo.getRepPersonId(), ordersInfo.getRepPersonName(),
        operDate, "1"
    );
    ordersRecordInfoService.insertOrdersRecordInfo(ordersRecordInfo);

    // 7. 发送短信通知
    this.sendMobileMessageMasCommon(operTypeCode, ordersId, ...);

    return ResultHelper.getResult(result);
}
```

### 11.5 解决了什么问题

1. **完整轨迹**：每次操作都记录到ordersRecordList，可追溯
2. **身份区分**：选民/群众 vs 代表，初始状态不同
3. **事务一致**：工单和记录同时插入或同时回滚

## 十二、面试综合建议与常见问题

### 12.1 面试技巧总结

#### 1. 如何描述技术方案

**STAR法则**：
- **Situation（背景）**：项目遇到了什么问题
- **Task（任务）**：我负责什么
- **Action（行动）**：我做了什么
- **Result（结果）**：取得了什么效果

**示例：**
> "（背景）系统上线后，用户反馈查询慢，最慢的接口要10秒。（任务）我负责性能优化。（行动）我引入了Druid监控，发现有一个分页查询没有索引，走了全表扫描，耗时8秒。我给street_id + status_code加了复合索引，又发现关联查询有N+1问题，改成了JOIN一次性查询。（结果）接口响应时间从10秒降到了200毫秒，提升了50倍。"

#### 2. 如何回答"你负责什么"

**避免**：说"我参与了XXX"
**应该**：说"我主导/负责了XXX"

#### 3. 如何回答"解决了什么问题"

**避免**：泛泛而谈
**应该**：具体数字 + 对比

### 12.2 常见面试问题及回答

#### Q1: 你们的架构是怎样的？

**回答：**
> "项目采用Dubbo+Zookeeper的分布式架构，分为4个模块：inpcs-rest作为HTTP入口，通过@Reference调用远程服务；inpcs-server作为业务逻辑层，通过@Service发布Dubbo服务；inpcs-core作为数据访问层；inpcs-web负责大屏展示。服务注册发现通过Zookeeper实现，注册地址是192.168.91.124:2181。"

#### Q2: 登录认证是怎么做的？

**回答：**
> "系统采用SSO单点登录。配置了SSO Client Filter，拦截所有HTML请求。首次访问时，Filter检测无Token，重定向到SSO认证中心；用户登录后，SSO生成Token写入Cookie；后续请求Filter从Cookie取出Token，调用SSO Server的/token/check接口验证有效性。验证通过后，用户信息（userId、personId、角色等）放入上下文，业务代码通过UserDto获取。同时通过excludePaths配置了公开接口不拦截。"

#### Q3: 四平台对接的签名是怎么做的？

**回答：**
> "对接新四平台时，采用HMAC-SHA256签名认证。流程是：1）生成随机字符串nonce和当前时间戳timestamp；2）将appId、nonce、timestamp、version按字母升序拼接；3）使用预共享的secret作为密钥，通过HMAC-SHA256对拼接字符串加请求体进行签名；4）将签名放入Authorization请求头。这样可以防止数据篡改、伪造身份、重放攻击。"

#### Q4: 短信通知是怎么实现的？

**回答：**
> "短信通知采用异步生产者-消费者模式。业务代码触发时，将操作类型、工单ID等信息封装成Map，放入ManageMassageSendMasHandler队列；异步线程从队列取出，根据操作类型匹配模板和接收角色。系统有5类角色：申报人、联络站代表、联络站站长、智联站联络员、办理人员。通过布尔参数组合实现精准匹配，比如群众反映时发给代表，代表上报时发给智联站。"

#### Q5: 性能优化做了哪些？

**回答：**
> "主要做了三方面优化：1）**慢SQL定位**：引入Druid监控，配置慢SQL阈值2秒，超过的SQL自动记录日志；2）**索引优化**：通过Druid定位到工单分页查询没有索引，给street_id+status_code建了复合索引；3）**连接池调优**：配置了Druid连接池参数initial-size=1、max-active=20、min-idle=1，合理控制连接数。"

#### Q6: Oracle迁移达梦做了什么改动？

**回答：**
> "迁移工作主要包括：1）**驱动替换**：从oracle.jdbc.driver.OracleDriver换成dm.jdbc.driver.DmDriver；2）**URL格式**：从oracle:thin:@host:port:sid变为dm://host:port/schema；3）**校验SQL**：从SELECT 'x'改为SELECT 1 FROM DUAL；4）**Hibernate方言**：配置为OracleDialect兼容模式；5）**Maven依赖**：添加达梦驱动Dm8JdbcDriver18。达梦对Oracle兼容性很好，大部分SQL不用改。"

#### Q7: 为什么用Dubbo不用Feign？

**回答：**
> "主要考虑三点：1）**性能**：Dubbo基于TCP长连接，序列化效率比HTTP高，适合内部高并发调用；2）**架构匹配**：项目是SSM架构，Dubbo对XML配置支持好，引入Feign需要额外集成Spring Cloud；3）**成熟度**：Dubbo在国内政务系统有大量案例，文档完善。"

#### Q8: Kafka和RabbitMQ有什么区别？

**回答：**
> "Kafka吞吐量更高（百万级/秒），支持消息回溯，适合日志采集、大数据场景；RabbitMQ功能更丰富，支持消息确认、死信队列，适合复杂的消息路由场景。政务系统的报警事件接入，数据量大、对持久化要求高，Kafka更合适。"
